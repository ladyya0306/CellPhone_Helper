# 离线私人智能助手 · APK 工程方案

> 战略决定（2026-10-17）：**停止投入离线网页界面，直奔 APK**。
> 理由：最终形态必然是 APK；网页方案在交互、通知、后台存活上都受限于浏览器，继续做是浪费。
> 本文替代方案书 §13 的"阶段 B"，并把所有可调项列为设置面板。

---

## 1. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **Kotlin** | 官方推荐，与 llama.cpp 的 JNI 桥接成熟 |
| UI | **Jetpack Compose** | 声明式，做聊天气泡/设置面板快 |
| 推理 | **llama.cpp + JNI（NDK 编译）** | 已验证可跑 GGUF；官方有 Android 示例 |
| 最低版本 | **Android 8.0 (API 26)** | 与 SmolChat/llama.cpp 示例一致 |
| 目标版本 | Android 15 (API 35) | 当前 AGP 稳定支持 |
| 后台 | **ForegroundService** | 唯一被系统认可的长驻方式，根治幽灵进程杀手 |
| 存储 | Room（SQLite） | 待办 / 记忆 / 会话历史 |
| 通知 | NotificationCompat + **RemoteInput** | 通知栏内直接回复，不回 App |
| 依赖注入 | 不引入（手写单例） | 控制 APK 体积与复杂度 |

**参考实现**（已克隆）：
- [SmolChat-Android](https://github.com/alifesoftware/SmolChat-Android-LLM) — Kotlin + llama.cpp 的完整可参考工程（`smollm/src/main/cpp/llm_inference.cpp` 是 JNI 桥）
- llama.cpp 官方 `examples/llama.android` — 最干净的 JNI 封装

**APK 体积策略**：模型**不打进 APK**（2.8GB 不可接受）。首次启动下载 + SHA256 校验 + 断点续传。APK 本体预计 **40–70MB**（含 arm64 原生库）。

## 3. 与现有 Python 实现的对应关系

| Python（已验证） | Kotlin（移植） | 说明 |
|---|---|---|
| `persona.py::safety_check` | `PersonaLayer.safetyCheck` | 正则表可直接搬 |
| `persona.py::force_tool` | `PersonaLayer.forceTool` | 同上 |
| `persona.py::inject_tic` | `PersonaLayer.injectTic` | 纯文本处理 |
| `persona.py::fix_break` | `PersonaLayer.fixBreak` | 注意：**只能诚实承认，不得否认身份** |
| `assistant.py::run_agent` | `AgentLoop.run` | 工具循环 |
| `assistant.py::system_prompt` | `PromptBuilder.build` | **必须保持恒定**（缓存） |
| `parse_when()` | `TimeParser.kt` | 含中文数字解析 |
| `tool_*` | `tools/*` | 改为原生 API（无需 Termux） |

**重要**：`persona.py` 的四条经验必须原样继承——
1. 安全拦截在模型**之前**
2. 工具由程序**强制**执行
3. 口癖由程序**注入**
4. 出戏修正**只能诚实承认，不能否认是 AI**

## 6. 关键技术风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **NDK 编译 llama.cpp** | 首次编译 10–20 分钟，可能遇到工具链问题 | 先照 llama.cpp 官方 Android 示例跑通最小用例 |
| **4B 内存 2.9GB** | 手机上 OOM 风险 | 默认 `-c 2048`；提供 2B 备选 |
| **prompt 缓存** | 系统提示一旦含时间/随机内容，每轮重算 2300 token（实测 60–80 秒） | 系统提示**必须恒定**，时间放用户消息 |
| **前台服务厂商限制** | vivo 需要白名单 | 首启引导用户加白名单 |
| **模型 2.8GB 下载** | 首启体验 | 断点续传 + 进度 + SHA256 |
| **APK 签名** | 自签名，后续版本需同签名 | 固定 keystore，妥善保存 |
| **上架** | Play 商店对后台常驻+本地大模型审核严 | 侧载分发 |

### 9.3 关键 bug 与修复

**Bug**：切换人设后模型仍用旧人格，提示语也不更新。

**根因**：`InferenceEngineImpl.setSystemPrompt` 有硬约束——
```kotlin
check(_readyForSystemPrompt) { "System prompt must be set ** RIGHT AFTER ** model loaded!" }
```
`_readyForSystemPrompt` 在首次设置后置 false，**第二次调用直接抛 IllegalStateException**。

**修复**：换人设时 `cleanUp()` → `loadModel()` → `setSystemPrompt()` 重载整套。
代价：切换耗时约 30–40 秒（2.4GB 模型重新加载），状态条会显示"正在切换…"。

## 10. M3 前置：JNI 工具调用扩展（2026-10-17 12:00）

按用户决定走 **A 方案：扩展 JNI**，把 llama.cpp 的 `common_chat` 能力暴露给 Kotlin。

### 10.1 新增的三个 JNI 入口（`ai_chat.cpp` 末尾）

| JNI 方法 | 作用 |
|---|---|
| `chatFormat(messages, tools): ByteArray` | 用 **完整 Jinja chat 模板 + tools** 渲染 prompt（`common_chat_templates_apply`） |
| `chatParse(text): ByteArray` | 用 **PEG 解析器**把模型输出解析成 tool_calls（`common_chat_parse`） |
| `processRawPrompt(prompt, nPredict): Int` | 把渲染好的整段 prompt 灌进 context |

**关键设计：一律用 `byte[]` 传数据。** 不用 `NewStringUTF`——它对中文/emoji 的 modified-UTF-8 处理会导致内容错乱。编码约定：字段 `\x1F` 分隔，记录 `\x1E` 分隔。

**Kotlin 侧**：`ToolCodec.kt` 负责编解码；`InferenceEngineImpl.sendToolPrompt()` + `parseToolCalls()` 是公开入口；`ToolCodec.ToolDef/ChatMessage/ToolCall` 是数据结构。

### 10.2 实测结果（决定性验证）

```
RAW: <tool_call>
{"name": "todo_add", "arguments": {"text": "明天下午三点开会"}}
</tool_call>

CALLS(1): todo_add({"text": "明天下午三点开会"})
```

**全链路打通**：渲染含工具的 prompt → 解码 → 模型产出 Qwen 格式 tool_call → PEG 解析器成功提取出结构化调用。

### 10.3 踩的坑

| 问题 | 原因 | 修复 |
|---|---|---|
| **原生崩溃 `SIGSEGV`** | `processRawPrompt` 解码时**没请求最后一个 token 的 logits**（`decode_tokens_in_batches` 的第 5 参数默认 false）→ 采样时 `n_outputs=0` → `get_logits_ith: invalid logits id -1` | 传 `true` |
| `override` 报错 | Kotlin 不允许 override 带默认参数 | 去掉实现里的默认值 |
| **Java 层 `Log.i` 完全看不到** | vivo ROM 吞掉第三方 App 的 Java 日志（原生日志正常） | 测试结果改**写文件** `files/tooltest.txt` 再读 |

> 第三条很值得记：**以后所有 App 内诊断都写文件**，不要依赖 logcat。

### 10.4 当前架构

```
Kotlin（AgentLoop，待写）
```

原因：当前 JNI 的 assistant 消息还不支持携带结构化 `tool_calls`，而多数 chat 模板要求
tool 消息必须紧跟"带 tool_calls 的 assistant 消息"，否则渲染报错。用 user 消息回灌
虽然不"协议纯净"，但**任何模板都能正确渲染**。等后续把 assistant 的 tool_calls 编码补上，再改回标准形式。

## 15. M6 缺陷修复（2026-10-17 19:05）

用户反馈"没感觉到心跳与会话连贯"，排查后发现**两个真实缺陷**（我的首次验证有盲区：
只验证了"重启后能恢复"，没验证"运行中能否实时看到"和"降频后能否恢复"）。

### 15.1 Bug A：自动降频变成"当天闭嘴"

**现象**：日志显示 `SILENT: 连续 6 次未响应，已自动暂停`，之后**整天再也不会开口**。

**原因**：v1 的设计是"连续 6 次未响应 → 当天暂停"。但用户打开 App 看了消息却没回复，
也被算作"未响应"，一旦累计到 6 次就永久静音——**这是设计缺陷，不是用户的问题**。

**修复**：
1. 改为**指数退避**而非硬停：3 次 → 间隔 ×2；6 次 → ×4；9 次 → ×8；**12 次才当天停**
2. `MainActivity.onResume` 重置 `hbUnresponded = 0` —— **回到 App 就算"看到了"**

### 15.2 Bug B：App 开着时心跳消息不出现

**现象**：心跳消息落库了，但界面不刷新，必须切走再切回（或重启）才看得到。

**原因**：`restoreHistory()` 只在模型加载完成时调用一次。

**修复**（三层）：
1. `onResume` 时刷新（切回 App 能看到）
2. **服务落库后发广播** `ACTION_HEARTBEAT` → App 注册的接收器立刻刷新
   （真正实现"App 开着时心跳直接出现在会话里"）
3. 心跳消息加 **💭 标记**，一眼区分"它主动说的"和"你问它答的"

### 15.3 Bug C：话术来回重复

**现象**：两条模板交替出现 4 次（"主人还有待办没做喵" / "小咪看到主人还有事情没做完喵"）。

**修复**：去重从"只比上一条"改为**"不与最近 4 条重复"**（`ArrayDeque` 保存最近 4 条）。

### 15.4 实测验证

App **保持在前台**，心跳触发后会话实时更新（截图确认）：

```
💭 主人今天辛苦啦喵～要不要歇一会儿
💭 主人还有待办没做喵～要不要小咪提醒你
💭 小咪看到主人还有事情没做完喵
...
```

数据库同步：`heartbeat` 来源消息从 1 条增至 2 条，`hb_unresponded` 在 onResume 后归 0。

### 15.5 教训（写给自己）

**验证不能只覆盖"重启后能恢复"，还要覆盖：**
1. **运行中**的实时性（用户看着的时候）
2. **降频/暂停后能否恢复**（否则一次触发就永久失效）
3. **重复内容的观感**（技术上"能说"≠ 体验上"不烦"）

下一次做 M9（心跳升级）时，这三条要作为验收清单。

## 17. facts 提取（2026-10-17 20:35）—— 记忆闭环

### 17.1 设计原则：**精确优先，宁可漏也不记错**

记错一条事实（把"不喜欢香菜"记成"喜欢香菜"）比漏记十条更伤信任。
所以只匹配**高置信度的显式表达**，不做模糊推断。

| 模式 | 例子 | 存成 |
|---|---|---|
| 记住XX | 记住我周五要交周报 | `周五要交周报` |
| 我不喜欢/不吃XX | 我不吃香菜 | `不喜欢香菜` |
| 我喜欢XX | 我喜欢喝冰美式 | `喜欢喝冰美式` |
| 我习惯XX | 我习惯晚上11点睡 | `习惯晚上11点睡` |
| 我生日是XX | 我生日是3月15日 | `生日：3月15日` |
| 我叫XX | 我叫小明 | `名字：小明` |
| 以后XX | 以后都叫我老板 | `以后都叫我老板` |
| 忘掉XX | 忘掉香菜 | 删除 key/value 命中"香菜"的事实 |

否定模式（`不|不太|不怎么|讨厌`）**必须先于肯定模式匹配**，否则"不喜欢"会被"喜欢"吃掉。

### 17.2 关键设计：把"系统实际做了什么"告诉模型

4B 模型会瞎编"我记住了"——即使程序什么都没做。所以提取后会往用户消息里插一句：

```
[系统已实际执行] 已记住：周五要交周报；已删除与「香菜」相关的记忆（1 条）。
请据此如实回答，不要说没做过的事。
```

注意这**仍然只放用户消息**，不进系统提示（否则破坏 prompt 缓存）。

### 17.3 实测：7/7 正确

| # | 输入 | 结果 |
|---|---|---|
| 1 | 记住我周五要交周报 | ✅ 存成 `周五要交周报`（多余的"我"已去掉）|
| 2 | 我不吃香菜 | ✅ 存成 `不喜欢香菜` |
| 3 | 我喜欢喝冰美式 | ✅ 存成 `喜欢喝冰美式` |
| 4 | 我习惯晚上11点睡 | ✅ 存成 `习惯晚上11点睡` |
| 5 | 我生日是3月15日 | ✅ 存成 `生日：3月15日` |
| 6 | 随便聊聊天气 | ✅ **正确忽略**（没记垃圾）|
| 7 | 忘掉香菜 | ✅ **成功删除**"不喜欢香菜" |

最终 facts 表：
```
· 生日：3月15日
· 习惯晚上11点睡
· 喜欢喝冰美式
· 周五要交周报
```

### 17.4 记忆管理界面（设置页）

- **已记住 N 件事** → 点开查看 / 全部清空
- **会话历史 N 条** → 点开清空（保留事实）
- 底部提示会告诉用户该怎么说

### 17.6 已知限制

| 项 | 说明 |
|---|---|
| 模型回复不总反映删除 | 说"忘掉香菜"后，事实确实删了，但 4B 回复仍说"记住了"。逻辑正确，模型表达不准 |

## 18. 动作执行修复（2026-10-17 21:20）—— "不懂装懂"专项

> 用户实测发现：让它设闹钟，**嘴上说设了，实际什么都没执行**。这是最伤信任的一类 bug。

### 18.1 三个独立缺陷（诊断结果）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 模型不调用工具 | 第一轮没调工具 → 代码当成"普通聊天"直接返回 |
| 2 | **不懂装懂** | 没有任何"说了但没做"的检测 |
| 3 | 闹钟没真正设置 | `EXTRA_SKIP_UI=false` 只是**打开时钟 App**，用户不点确认等于没设 |

### 18.2 修复：三层防"嘴上答应"

**第 1 层：动作意图检测 + 强制指令**

```kotlin
val wantsAction = ACTION_HINTS.any { userText.contains(it) }
// 闹钟/待办/日程/提醒我/叫我/帮我加/定个/设个/安排/记一下
if (wantsAction && tools.isNotEmpty()) {
    append("[系统指令] 用户要你**执行操作**。你必须调用对应的工具，不要只用文字回答。")
}
```

**第 2 层：调了工具但全失败 → 不进第 2 轮**

```kotlin
if (steps.isNotEmpty() && steps.all { it.result.startsWith("失败") }) {
    return Result("（没能完成——系统执行时出错了：）\n· tool：原因", steps)
}
```
否则模型会把失败"圆"成成功。

**第 3 层：没调工具却声称做完了 → 诚实拒绝**

```kotlin
if (calls.isEmpty() && wantsAction) {
    val claimed = rawText.contains("已") || ... 
    return Result("（抱歉，这次我没能真正执行——系统没有检测到任何操作被执行，所以我不能说我做完了。）", ...)
}
```
这条会以 `source="refusal"` 落库，便于事后审计。

### 18.3 修复：闹钟真的能设

```kotlin
putExtra(AlarmClock.EXTRA_SKIP_UI, true)   // 原来 false = 只打开 App
```

**实测验证**（dumpsys alarm）：
```
time:1792278000000 = 2026-10-18 07:00:00.000
tag=*walarm*:com.cn.google.AlertClock.POWER_ALARM_ALERT
procName=com.android.BBKClock          ← vivo 时钟真的收到并设了
```

### 18.4 新增：日程写进系统日历

`calendar_add` 工具 → `CalendarContract.Events` 插入，需要 `READ/WRITE_CALENDAR`。

**实测验证**（content provider 查询）：
```
Row: 406 title=充电提醒, dtstart=1792274400000  → 2026-10-18 06:00 ✓
```

### 18.5 关键 bug：模型不知道今天几号

第一次测试时它把"明天6点"解析成 **2024-03-15**（拿错了"生日3月15日"这条记忆，年份还编了）。

**修复**：用户消息前缀注入当前时间（**不进 system prompt，保缓存**）：
```
[现在是 2026-10-17 21:04 星期五]
```
修复后同一句话正确解析为 **2026-10-18 06:00** ✓

另外 `calendar_add` 增加了**过去日期拒绝**，防止模型编年份。

### 18.6 新增：设置页「▶ 立即发一条试试」

因为 4 小时内容冷却会挡住手动验证，加了一个按钮：跳过所有闸门，直接发一条。
实测日志：`21:15:17  MANUAL: 剩那么多，你是打算拖到什么时候。`
消息以 `source=heartbeat` 落库（#90），同时出现通知。

### 18.7 回归测试（4/4 通过）

| # | 输入 | 工具调用 | 结果 |
|---|---|---|---|
| 1 | 帮我设定明天6点的日程 | `calendar_add` 1 次 | 2026-10-18 06:00 写入系统日历 ✓ |
| 2 | 加一条待办：明天下午三点开会 | `todo_add` 1 次 | 待办 #4 ✓ |
| 3 | 设个闹钟：明天早上七点 | `alarm_set` 1 次 | 系统闹钟 07:00 ✓ |
| 4 | 今天天气怎么样 | 0 次（正确） | 闲聊，不误触发 ✓ |

### 18.8 剩余瑕疵

| 项 | 说明 |
|---|---|
| 措辞混淆 | 写日历事件时，模型说"设了闹钟"（把 calendar 和 alarm 混着说）。动作对，措辞不准 |

## 19. 架构重构：动作账本 + 多会话（2026-10-18）

> 详见 **[架构诊断与重构方案-2026-10-18.md](架构诊断与重构方案-2026-10-18.md)**。要点：

- 原则改为"**程序说事实，模型说情绪**"：确定性意图路由 + 中文时间解析 + 动作账本（执行后核验）+ 声明守卫（逐句删除无账本支撑的承诺）+ 程序回执。

- 验证：虚拟机 Kotlin 全量编译通过；回归语料 101/101 通过；**尚未打包与实机验收**（验收清单见上述文档 §3.4）。
