# 共享节拍图与透镜（2026-10-22）

> 决定：不再给 14 个人设各写 360 天话术。改成 **1 张共享话题/节拍图 + 14 张人设透镜 + 1 个渲染器 + 1 套世界状态**。
> 下一步：**L1 = 20 个共享节拍 × 3 个人设透镜（小咪/零/傅沉）× 10 天 × 4 轮**，PC 对照测试。

## 一、为什么改

14 人 × 360 天 = 5,040 个“人设日”；手写是 5,040 套脚本。  
但聊天不是 5,040 个孤立句子，而是**同一批生活/社交节拍，由不同人用不同立场说出来**。

- 共享：节拍、话语行为、前置条件、效果、世界事实；
- 每人一张：立场、知识、目标、秘密、道具、口癖、边界；
- 渲染：模板/小模型只负责“把事实说成她”；
- 状态：话题栈、未闭合问题、承诺、belief、关系、剧情旗标。

## 二、三层架构

```text
WorldState（时间/天气/事件/事实）
  ↓
DialogueState（话题栈/未闭合问题/承诺/情绪/风格）
  ↓
BeatGraph（共享：节点=对话节拍，不是主题词）
  ├─ speechAct：问/答/安慰/调侃/拒绝/转移/收束
  ├─ requires：用户意图/关系/剧情/时间
  ├─ effects：关系/记忆/旗标/open_loop
  └─ roles：谁适合说、谁只能旁观
  ↓
PersonaLens（14 张）
  ├─ stance：她怎么看这件事
  ├─ knowledge：她知道/不知道
  ├─ goals/secrets/props/taboos
  └─ voice DNA
  ↓
Renderer（模板 / 小模型）
  ↓
Guard（事实/重复/安全/人设/长度）
```

数据：

```kotlin
data class BeatNode(
    val id: String, val domain: String, val speechAct: String,
    val requires: List<String>, val effects: List<String>,
    val roleTags: List<String>, val slots: List<String>
)
data class PersonaLens(
    val personaId: String, val stance: String,
    val knows: List<String>, val doesntKnow: List<String>,
    val goals: List<String>, val props: List<String>,
    val voice: String, val taboos: List<String>
)
```

## 五、DialogueState / WorldState

```text
WorldState: day, weather, events, facts
DialogueState:
  topic_stack: [meal, work, ...]
  open_loops: [{what, due, personaId}]
  commitments: [...]
  beliefs: {personaId: facts they know}
  relationship: affinity/trust/tension
  style_mode: NORMAL/TVB/...
  recent_topics: last 30
```

规则：

- 用户问题未回答前，不主动切话题；
- 切话题必须走 B18 桥接；
- 同一事实只由知道的人说；不知道就承认不知道；
- 承诺写 `open_loops`，下次由程序接，不靠模型记。

**机器门禁**：A/B/C 都过 0 重复、0 超长、0 编造。

**但 A/B 的差异很小**：两者都没有编造；B 只是平均字数略长、动作略多。  
**新架构的真正价值在 C**：同一套 20 节拍 + 状态机，零和傅沉能产出明显不同的话：

### 补算：话题丰富度 / 主动发问 / 上下文回指

脚本：`scripts/l1-analyze.py`；结果：`run/l1/analysis.md`。

| 指标 | A 旧架构 | B 新架构 |
|---|---|---|
| 主动发问（含问号） | 4/40（10%） | **2/40（5%）** |
| 非首轮主动发问 | **3** | **0** |
| 上下文回指（刚才/之前/那…） | 0 | 1 |
| “好吃吗”回应含主菜 | 3/10 | **5/10** |
| 非当前话题的新事实 | **4** | **7** |

| 二元组 TTR（越高越多样） | **0.706** | **0.633** |

解读：

- **主动发问：A 更好**（4 vs 2；非首轮 3 vs 0）。B 的“只执行当前节拍”把追问也压掉了。
- **话题多样：A 更好**（TTR 0.706 vs 0.633）。B 更集中，但集中不等于丰富。
- **上下文：B 略好一点**（“好吃吗”带主菜 5/10 vs 3/10；回指 1 vs 0），但两边都很少显式回指。
- **B 的副作用**：非当前话题的新事实更多（7 vs 4）、“蹭蹭”更多（8 vs 2）。

**所以：新架构当前版本没有在“丰富度/主动发问”上赢；它只证明了可复用和安全性，没有证明更像活人。**

### L1b：A + B 混合架构（H）

不再让 B 用“限制”替换 A 的内容，而是：

```text
A 的内容/事实基线（360 天 LifeCard + 内容银行）
  + B 的节拍/透镜/状态
  + 复合策略：答完 → 追问 / 扩展 / 桥接 / 收束
```

#### 复合节拍策略

每个回复允许：

| 动作 | 规则 |
|---|---|
| ANSWER | 先答用户当前问题；meal/work 必须落到 LifeCard 事实 |
| FOLLOWUP | 30–50% 轮次追加一个相关追问；不是每轮都问 |
| EXPAND | 最多追加 1 个相关事实（事件/钩子），不是随便加塞 |
| BRIDGE | 切话题时用“说到这个…”；不硬切 |
| CLOSE | 收束/晚安/保留 open_loop |

长度：2–3 句、≤60 字；不再强制“只回一句”。

#### 三组

| 组 | 内容 | 策略 | 轮数 |
|---|---|---|---|
| **A** | 小咪 360 天语料 | 旧：直接 LifeCard + 人设 | 40（已有） |
| **B-old** | 同一 10 天事实 | 单节拍、单事实、单句 | 40（已有） |
| **H 混合** | 同一 10 天事实 + 360 天储备入口 | 节拍 + 透镜 + 状态 + 复合策略 | 40（新跑） |

A/B-old 数据已存在；只新跑 H，同一 10 天、同一用户脚本、同一模型、同一 4 轮历史。

#### H 的提示词顺序

1. 人设/声音（圣经/透镜）；
2. 今日 LifeCard 事实；
3. 当前节拍 + 复合策略（答/追问/扩展/桥接）；
4. 状态（话题栈/open_loop/最近说过）；
5. 安全与去重（最后，且短）。

#### H 的门禁

| 指标 | 目标 |
|---|---|
| 主动发问 | ≥ A（≥4/40） |
| 非首轮主动发问 | ≥ A（≥3） |
| 二元组 TTR | ≥ A（≥0.70） |
| 上下文回指 | ≥20% |
| 非当前话题新事实 | ≤ A（≤4） |
| 编造/串味 | 0 |
| 精确重复 | 0 |
| >60 字 | ≤5% |
| 人工“像她” | ≥4/5 |

**H 的进步**：

**H 仍未过**：

- 上下文回指只有 4/40（10%），未到 20%；

#### H4 修正

1. 追问句加 6–8 个变体，禁止连续重复“主人今天吃了什么”；
2. 在 2 个轮次强制“刚才你说…”回指（目标 ≥8/40），但不要每轮都带；
3. CompanionGuard 扩到“和…猫/新猫/阿壹一起吃”，卡里没写就不许；
4. 扩展只允许 1 个当前场景事实，不能把三餐/工作/事件都塞进来；
5. 再跑 40 轮；仍不过就不扩 14 人。

4. 扩展只允许 1 个**同类**事实（吃饭→事件），不允许三餐/工作混塞；
5. 再跑 40 轮；仍不过则接受“H 只在复用层有价值，单聊仍用 A”。
