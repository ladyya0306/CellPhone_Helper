## 一、产品定位

### 1.1 一句话定位

> **一个跑在你手机里的伙伴：平时是说到做到的小秘书，空闲时是陪你玩的玩伴；它会摸清你的闲忙节奏，在合适的时候主动开口；你们的共同经历会一点点积累下来，数据只在你的手机里。**

### 1.2 两个角色，一条主线

| 角色 | 负责什么 | 关键要求 |
|---|---|---|
| **小秘书** | 待办、提醒、闹钟、日程、每日简报、当日资讯 | 说到做到，每件事可核对；没做成就明说 |
| **玩伴** | 轻量小游戏、伙伴的"出发与归来"冒险、闲聊 | 有性格、有分寸、不制造负担 |
| **主线：共同成长** | 关系与共同经历的积累：回忆、梗、纪念品、里程碑 | 只增不减，不以惩罚驱动 |

### 1.3 差异点（与市面产品相比）

| 差异点 | 说明 | 竞品为何不易跟进 |
|---|---|---|
| ① 说到做到、可以核对 | 所有动作经过程序执行与核验，回执单独显示，设置页可查全部动作记录；模型的虚假承诺被程序删除 | 云端大模型助手普遍"重能力、轻核验"，改造成本高 |
| ② 摸清闲忙再开口 | 基于本地回应记录、日程与作息学习"什么时候适合说话"，而不是定时推送 | 需要长期、私密的本地行为数据，云端产品有隐私顾虑 |
| ③ 共同成长而非数值养成 | 成长体现为共同经历、回忆与解锁内容，冷落不倒退 | 主流陪伴产品依赖留存与付费机制，与此方向相反 |
| ④ 数据主权 | 对话、记忆、作息全部本地；联网只下载公开资讯，逐项可见、可关 | 大厂商业模式依赖账号与数据 |

### 1.4 目标用户

1. 首要用户：开发者本人（自用验证，所有功能先满足"自己每天会用"）。
2. 第二圈：对隐私敏感、反感强推送与成瘾设计、愿意侧载 APK 的成年用户。
3. 暂不面向：未成年人（见 §12.5 合规）。

### 1.5 明确不做

- 不做恋爱化、成人向内容；不模拟真人关系；不承诺"永远陪着你""你是我的唯一"。
- 不做压力型养成：好感度数字、每日签到奖励、断签清零、"不来它会难过"。
- 不在后台上传任何个人数据；不以对话数据训练模型。
- 不做付费墙、抽卡、内购。

## 二、现状与缺陷总表

### 2.1 已完成里程碑

M1 跑通 4B 模型 → M2 会话窗口与设置页 → M3 JNI 工具调用 → M4 危机前置拦截 → M5 心跳前台服务 → M6 记忆与会话持久化 → M7 架构重构（动作账本、到点提醒、多会话；2026-10-18，**待实机验收**）。

### 2.2 缺陷与处理状态

| # | 缺陷 | 根因 | 处理方法 | 状态 |
|---|---|---|---|---|
| 1 | 闲聊轮模型声称"已设闹钟""记住了"，实际未执行 | 守卫只在用户话含动作关键词时生效 | `ClaimGuard` 逐句检查每一轮输出，无账本支撑即删除并说明 | 已改，待实机验收 |
| 2 | "到时候提醒你"无法兑现 | 无任何到点触发机制 | `ReminderScheduler`：精确定时、持久化、开机重登记、触发留痕 | 已改，待实机验收 |
| 3 | 闹钟报成功但未生效；"后天7点"被设成下一个7点 | 发出 Intent 即报成功；系统接口只支持 24 小时内 | 系统时钟 + 自动核对；超范围或被拦截时改用助手闹钟 | 已改，待实机验收 |
| 4 | 日程写入但不提醒 | 只设 `HAS_ALARM`，未插 `Reminders` 行 | 补插提醒行并回读核验 | 已改，待实机验收 |
| 5 | 待办写入失败仍回答"已加入" | 写文件异常被吞掉 | 原子写、失败抛出、回读核验 | 已改，待实机验收 |
| 6 | 历史"教"模型撒谎、回复复读 | 只存 assistant 声明，不存执行痕迹；心跳模板混入上下文 | 回执单独落库并以"系统回执"附注进入上下文；心跳、提示不进上下文 | 已改，待实机验收 |
| 7 | 切走 App 后一轮被取消，输入框卡死 | 协程绑定 Activity 并在 `onStop` 取消 | 进程级运行时 `AssistantRuntime` | 已改，待实机验收 |
| 8 | 换人设后人格串味 | 单一会话，旧人设历史喂给新人设 | 多会话、一会话一人设 | 已改，待实机验收 |
| 9 | 换人设要等 30–40 秒 | 每次重载 2.4GB 模型（实无必要） | 换人设即开新会话，不重载 | 已改，待实机验收 |
| 10 | 返回键后再开必报"模型加载失败" | `onDestroy` 销毁进程级单例 | 不再销毁单例引擎 | 已改，待实机验收 |
| 11 | 一次出错后引擎永久不可用 | prompt 失败后状态未复位 | 复位状态并抛出明确异常 | 已改，待实机验收 |
| 12 | 每句话硬塞全部记忆；记忆干扰时间解析 | 每轮全量注入事实 | 相关性筛选（≤3 条，称呼常驻） | 已改，待实机验收 |
| 13 | 误提取事实（"我不想上班""我是学生"等） | 正则过宽 | 收紧规则 + 冲突槽位归一 | 已改，语料已通过 |
| 14 | 清空事实时连聊天记录一起删除 | 调用了 `clearAll()` | 改为 `clearFacts()` | 已改 |
| 15 | 每轮 20–50 秒延迟 | JNI 每轮清空 KV 缓存整段重算，"prompt 缓存"从未生效 | 前缀 KV 缓存（§10.1） | **未修复** |
| 16 | prompt 超长时截掉末尾（可能截掉用户最新一句） | C++ 端从尾部截断 | Kotlin 侧按 token 预算从历史一侧裁剪 | **未修复** |
| 17 | 无法取消/修改系统时钟里的闹钟 | Android 无公开接口 | 助手提醒可在设置页取消；系统闹钟引导用户到时钟里改 | 部分处理 |
| 18 | 记忆明文存储 | 测试阶段未加密 | 公开发布前上 SQLCipher（§12.5） | **未修复** |
| 19 | 模型需 adb 推送，普通用户无法安装 | 无模型管理 | 模型下载 / 从文件导入（§12.2） | **未修复** |

### 2.3 过程层面的教训（写入开发规范）

1. 每发现一个"说了没做 / 记错 / 解析错"，**先把原话加进 `AssistantSelfTest`，再改代码**。
2. "完成"必须附证据：编译输出、自检报告、数据库查询、实机截图；只凭实现者自述不算完成（同样适用于 AI 编程助手）。
3. 调试包与正式包分离，测试数据不进日常数据库（§11.2）。

## 三、总体架构

```
┌───────────────────────────────── 表现层 ─────────────────────────────────┐
│ 会话窗口（话语 / 回执 / 提示分层显示） · 通知（可回复） · 游戏卡片 · 成长手账 │
├───────────────────────────────── 调度层 ─────────────────────────────────┤
│ 心跳调度：闲忙模型 → 时段选择 → 内容选择（简报/提醒/游戏/冒险）→ 打扰闸门    │
├───────────────────────────────── 对话层 ─────────────────────────────────┤
│ ①安全拦截 → ②意图路由与补槽 → ③执行与核验（动作账本）→ ④模型生成 → ⑤声明守卫 │
├──────────────────────────────── 能力模块 ─────────────────────────────────┤
│ 秘书：待办 提醒 闹钟 日程 简报 资讯   │   玩伴：游戏框架 小游戏 冒险 成长        │
├──────────────────────────────── 数据层 ──────────────────────────────────┤
│ 用户层（共享） · 世界层（共享） · 伙伴层（各人设独有） · 动作账本（审计）       │
├──────────────────────────────── 推理层 ──────────────────────────────────┤
│ llama.cpp JNI（本地）  ·  云端交接 L2（可选，每次确认）                       │
└──────────────────────────────────────────────────────────────────────────┘
```

**不变量**（任何改动不得破坏）：
1. 用户看到的"做了什么"只来自动作账本，不来自模型文本。
2. 无法核验的结果必须如实标注"未能确认"。
3. 程序承诺的能力必须有对应的执行机制。
4. 游戏的随机、规则、胜负、存档全部由程序掌握，模型只负责旁白。
5. 模型上下文只包含真实对话；模板、回执、系统提示不得冒充 assistant 发言。
6. 主动消息必须经过打扰闸门。

## 四、三层记忆模型

### 4.1 分层与归属

| 层 | 内容 | 归属 | 进入模型上下文的方式 |
|---|---|---|---|
| **用户层** | 事实与偏好、待办、提醒、日程、作息规律 | 所有人设共享 | 按相关性挑选 ≤3 条，称呼常驻 |
| **世界层** | 纪念品与收藏、已解锁冒险地点、里程碑、"小屋"陈设、世界日志（谁和你做过什么，只记事件不记内容） | 所有人设共享 | 话题相关时带一两条 |
| **伙伴层** | 会话与会话摘要、共同经历、对局战绩、专属称呼与梗、关系阶段 | 每个人设独有 | 当前人设的相关摘要与经历 |
| **动作账本** | 每次执行、核验结果、被拦截的虚假承诺 | 审计用，不属于记忆 | 不进入 |

**设计理由**：秘书职责要求所有人设都了解用户（换人设就忘了你周五交周报属于失职）；关系则应各自独立，世界保持连贯。人设之间只能通过世界日志"听说"彼此的经历（"听说你和小咪去了海边"），看不到彼此的对话内容。

### 4.2 隐私控制

| 机制 | 规则 |
|---|---|
| 树洞人设 | "树洞·听"默认**不向用户层与世界层写入任何内容**，说过的话只留在它自己的伙伴层 |
| "只告诉你" | 对任一人设说"这个只告诉你"，本句不进入用户层 |
| 可见可改 | 设置页可查看、编辑、删除每一条事实与摘要；可一键导出 JSON、一键清空 |
| 忘掉 | "忘掉XX"物理删除命中记录，并给出回执 |

### 4.3 数据结构（在现有 `memory.db` v2 基础上扩展为 v3）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `facts`（已有） | key, value, slot, updated_at, last_used_at, **source_msg_id**, **scope**(global/private) | 增加来源与可见范围 |
| `conversations`（已有） | id, persona_id, title, **summary**, **summarized_at** | 会话摘要在空闲且充电时生成 |
| `episodes`（新增） | id, persona_id, type(adventure/game/milestone/chat), title, detail, created_at | 伙伴层共同经历 |
| `world_items`（新增） | id, item_key, found_by_persona, found_at, placed | 世界层收藏 |
| `world_log`（新增） | id, persona_id, event, created_at | 世界日志（只记事件） |
| `rhythm`（新增） | weekday, hour, sent, responded, busy_hits | 闲忙模型（§6） |
| `game_state`（新增） | game_id, persona_id, state_json, updated_at | 游戏存档 |

## 五、人格系统

1. **精简主线人设**：九个人设并行打磨成本过高。建议主线保留三到四个（例如：猫娘·小咪、傲娇大小姐·凛、温柔大姐姐·绫，外加特殊定位的树洞·听），其余作为可选，待内容充实后再开放。
2. **人设 = 数据**：系统提示、口癖后处理、程序短句（`PersonaVoice`）、心跳话术、游戏台词、冒险旁白风格，全部按人设配置。
3. **会话绑定**：一个会话属于一个人设；换人设即开新会话或切回该人设的旧会话（已实现）。
4. **关系阶段代替好感度**：不显示数值；以里程碑推进阶段（初识 → 熟悉 → 默契），阶段解锁新话题、新称呼、新游戏台词。只进不退。
5. **身份诚实**：扮演不等于否认身份；首次使用与定期（见 §12.5）提示"你在与 AI 互动"。

## 六、心跳与闲忙学习

### 6.1 数据来源（全部本地）

| 来源 | 用途 | 权重 |
|---|---|---|
| 用户手动设置（上班、午休、免打扰） | 硬约束 | 最高，程序推断不得覆盖 |
| 日历事件、带时间的待办 | 标记忙碌时段 | 高 |
| 对主动消息的回应 / 忽略 | 学习回应率 | 中 |
| 用户主动打开 App 的时段 | 学习空闲时段 | 中 |

### 6.2 闲忙模型

- 维护"一周七天 × 24 小时"的回应率表（`rhythm`）：`回应率 = (responded + 1) / (sent + 2)`（平滑，避免样本少时极端）。
- 冷启动：前两周按手动设置与默认节奏运行，同时积累数据。
- 时段选择：在未被日程占用、不在免打扰内的时段中，选回应率最高者；同一天内两次主动消息间隔不少于 2 小时。

### 6.3 每日节奏（默认，可调）

| 时段 | 内容 | 角色 |
|---|---|---|
| 早间（用户通常最早有回应的时段） | 今日简报：今日待办、提醒、天气或一条资讯 | 秘书 |
| 午间 / 空档 | 小游戏邀请，或"我出发去冒险了" | 玩伴 |
| 下午空档 | 冒险归来的明信片 | 玩伴 |
| 晚间 | 今日回顾：完成了什么、成长手账新增 | 秘书 + 玩伴 |

**每日上限**：有内容的主动消息默认 3–4 条；到点提醒不计入上限（用户明确要求的）。

### 6.4 打扰闸门（沿用并扩展现有实现）

免打扰时段、用户刚发言后静默、电量下限、每日上限、同内容冷却、连续未回应指数退避；新增：日程忙碌时段静默、正在游戏中不推送其他内容、持续使用超过 2 小时时提示休息（§12.5）。

## 七、秘书能力

| 能力 | 现状 | 下一步 |
|---|---|---|
| 待办（增 / 查 / 完成） | 已实现，带时间的待办自动登记提醒 | 修改、删除、按日期查看 |
| 到点提醒 / 计时 | 已实现 | 修改、推迟（"再过十分钟提醒我"） |
| 闹钟 | 已实现（系统时钟 + 核对 + 助手闹钟兜底） | 助手闹钟的全屏响铃界面 |
| 日程 | 已实现（写入系统日历 + 提醒） | 查询今日 / 明日日程 |
| 每日简报 | 未实现 | 由程序汇总待办、提醒、日程，模型只加一句人设开场 |
| 当日资讯 | 未实现 | 见 7.1 |

### 7.1 资讯模块的联网边界

资讯必须联网，与"离线"定位存在矛盾，按以下原则处理，确保宣传口径成立：

1. **只下载、不上传**：每天固定时间拉取用户自选的资讯源（RSS 等公开源），请求中不携带任何个人数据。
2. **授权且可见**：设置页总开关默认关闭；每次拉取记入动作账本。
3. **本地处理**：下载后由本地模型在空闲时筛选、改写为人设口吻；标注来源与"AI 改写"。
4. **对外表述**：使用"对话与记忆不出手机"，不再使用"完全不联网"。

## 八、玩伴能力

### 8.1 游戏框架（先于具体游戏实现）

| 组件 | 职责 |
|---|---|
| `GameRegistry` | 注册游戏：id、名称、触发说法、适用人设 |
| `GameSession` | 统一生命周期：开始 → 回合 → 结束 → 存档；同一时间只进行一局 |
| 规则引擎 | 程序掌握随机种子、规则、胜负；**先由程序决定伙伴的出招，再接收用户输入**，确保公平 |
| 台词表 | 按人设、按事件（开局 / 胜 / 负 / 平 / 连胜）配置，不调用模型 |
| 战绩 | 写入伙伴层（`episodes`），供闲聊与心跳引用 |
| 触发 | 意图路由识别"来一局石头剪刀布"；心跳可发起邀请（受闸门约束） |

### 8.2 第一层：即开即玩（每局一分钟内）

石头剪刀布、掷骰子比大小、抽签、自写的"答案之书"、猜数字。
注意：市面"答案之书"文本受版权保护，须自行编写答案库（初版 200–300 条，可按人设分别撰写）。

### 8.3 第二层：文字小冒险

3–5 分钟一局，事件卡片驱动（数据文件定义），用户在 2–3 个节点做选择；程序管状态，模型只在关键节点写一两句旁白（可关闭）。

### 8.4 "出发与归来"（共同成长的核心玩法）

1. 伙伴每天可出发 1–2 次（用户邀请或心跳择时）；程序生成 3–5 个事件的旅程，用户在途中做 2–3 个选择。
2. 失败无损失，只是带回的故事不同。
3. 归来时寄回明信片 / 故事卡 / 纪念品，进入世界层收藏，摆进"小屋"。
4. **与记忆联动**：旅程内容引用用户层信息（喜欢冰美式 → 路过咖啡馆，带回咖啡豆），使每个人的伙伴与故事都不相同。
5. **与现实联动（可选，默认开启，可关）**：完成待办、按时休息，为下一次出发增加"补给"；只加分、不扣分，绝不说"你又没做到"。

## 九、成长规则与护栏

| 规则 | 说明 |
|---|---|
| 成长来源 | 真实互动：一起冒险、游戏、聊天、托付的事办成；不以挂机时长计 |
| 成长表现 | 里程碑、关系阶段、解锁新话题 / 游戏 / 冒险地点 / 台词；不显示数值 |
| 只增不减 | 冷落不倒退；长期未使用时伙伴"更安静"，不表达委屈或内疚 |
| 无签到 | 不设每日奖励、连续天数奖励、断签惩罚 |
| 时长提示 | 连续使用超过 2 小时提示休息 |
| 可退出 | 一键关闭玩伴功能，秘书功能不受影响；可重置成长而不影响用户层记忆 |
| 危机优先 | 危机前置拦截优先于一切玩法 |

## 十、性能

### 10.1 前缀 KV 缓存（优先级最高的未修复项）

现状：`processRawPrompt()` 每轮调用 `reset_long_term_states()` 清空 KV，系统提示、工具定义与历史全部重算。改为与上一轮 prompt 比较公共前缀，只删除分叉点之后的 KV、只解码差异部分（代码草案见《架构诊断与重构方案》§四）。配合要求：系统提示与工具定义置于 prompt 最前且逐字不变（已满足）。预期：第二轮起首字延迟下降一半以上，以实测为准。

### 10.2 其他

| 项 | 措施 |
|---|---|
| 确定性路径 | 秘书指令与游戏不调用模型，秒级响应（已实现） |
| 上下文裁剪 | Kotlin 侧按 token 预算从最早历史裁剪，C++ 不再截尾 |
| 机型分档 | 12GB 以上：4B；8GB：2B 或 1.7B；内存不足时自动降级并提示 |
| 后台生成 | 会话摘要、资讯改写只在空闲且充电时进行 |

## 十二、APK 封装与发布

### 12.1 构建配置

| 项 | 方案 |
|---|---|
| 签名 | 用 `keytool` 生成专用发布密钥库（RSA 2048，有效期 25 年以上）；密码写入不入库的 `keystore.properties`，`build.gradle.kts` 的 `signingConfigs.release` 读取。**密钥库至少异地备份两份**：丢失后已安装用户无法覆盖升级 |
| 构建类型 | release：开启 R8 混淆与资源压缩（当前 debug 也开启了，建议 debug 关闭以便排查） |
| ABI | 仅 arm64-v8a（现状 57–60MB） |
| 版本号 | `versionName` 采用 `主.次.修订`（如 0.7.0 对应 M7）；`versionCode` 单调递增（如 `主×10000 + 次×100 + 修订`） |
| 产物命名 | `CompanionAssistant-0.7.0-arm64.apk`，同时发布 SHA256 |
| 构建命令 | `. .\env-build.ps1` 后执行 `& $GRADLE :app:assembleRelease` |

### 12.2 模型分发（当前最大的安装障碍）

| 项 | 方案 |
|---|---|
| 不打包进 APK | 模型 2.4GB，单独分发 |
| 首次启动引导 | 检测机型内存 → 推荐模型档位 → 二选一：①应用内下载（断点续传、SHA256 校验、仅 Wi-Fi 默认）②从手机文件导入（系统文件选择器，适合用电脑拷贝后导入） |
| 下载源 | 国内用户访问 Hugging Face 不稳定，需准备国内镜像（如 ModelScope 或自备对象存储），在设置页可切换 |
| 校验 | 每个模型档位内置文件大小与 SHA256；校验失败不加载 |
| 模型管理页 | 查看已装模型、切换、删除、释放空间 |

### 12.3 首次启动引导（Onboarding）

1. 身份说明：这是 AI，不是真人；数据存放在本机。
2. 权限逐项申请并说明用途：通知、日历、精确闹钟。
3. 厂商后台保活引导：电池优化白名单、自启动、vivo"应用跳转确认"选"始终打开"（逐品牌给出图文步骤）。
4. 作息设置：上班时段、午休、免打扰（闲忙模型的冷启动依据）。
5. 选择第一个伙伴。
6. 运行一次自检并展示结果。

### 12.4 发布渠道（分阶段）

| 阶段 | 渠道 | 适用条件 |
|---|---|---|
| ① 自用 | adb / 文件直装 | 当前 |
| ② 小范围内测（10–30 人，熟人） | 直接分享 APK 与模型下载说明 | 发布门槛（§11.3）通过；附隐私说明与反馈渠道 |
| ③ 公开侧载 | 代码托管平台的 Release 页或自建页面 | 完成 §12.5 中"公开前必做"各项 |
| ④ 国内应用商店 | 各手机厂商商店 | 需 APP 备案等资质（见 §12.5），个人开发者门槛较高，暂不规划 |

### 12.5 合规要点

> 以下为对现行规定与征求意见稿的梳理，**不构成法律意见**；正式公开发布前应以最新官方文本为准，必要时咨询专业人士。

**（1）APP 备案**：在境内应用商店上架的应用需办理 APP 备案，未备案可能被下架、责令改正；备案材料与主体以企业为主要语境。阶段 ①–③ 不涉及应用商店上架；阶段 ④ 前须专门研究。

**（2）生成式人工智能与算法相关规定**：面向公众提供生成式 AI 服务涉及安全评估与备案等义务；本产品为本地模型、离线运行、不提供在线服务，但若公开分发并加入云端交接，适用情况可能变化，阶段 ③ 前须专门评估。

**（3）《人工智能拟人化互动服务管理暂行办法（征求意见稿）》**（国家网信办 2025-12-27 发布，尚为征求意见稿）与本产品直接相关，主要要求与对照如下：

| 征求意见稿要求 | 本产品对照 | 措施 |
|---|---|---|
| 显著提示用户在与 AI 互动；首次使用、再次登录、出现过度依赖倾向时弹窗提示 | 已有"扮演不否认身份"原则 | 首启说明 + 定期提示（新增） |
| 连续使用超过 2 小时弹窗提示暂停 | 无 | 新增（§9） |
| 不得以替代社会交往、诱导依赖为设计目标；设置依赖风险提示 | 与"不做压力型养成"一致 | 写入护栏 |
| 高风险情形使用预设回复并引导专业帮助；明确自杀自伤意图时人工接管并联系监护人或紧急联系人 | 已有危机前置拦截与求助资源 | 新增"紧急联系人"设置与一键拨打；个人离线产品无法提供人工接管，**这是公开发布的重大障碍之一**，需在阶段 ③ 前评估 |
| 未成年人模式、监护人同意与管控 | 当前不面向未成年人 | 公开发布须加入年龄提示与未成年人模式，或明确限制 |
| 老年人：鼓励设置紧急联系人，不得模拟亲属关系 | 不模拟真人关系 | 紧急联系人（同上） |
| 交互数据加密、访问控制；可删除聊天记录；未经单独同意不得用于训练 | 已可删除；不训练；**目前未加密** | 公开前上 SQLCipher |
| 提供便捷退出 | 可关闭玩伴功能 | 增加"结束对话"按钮与关键词 |
| 达到一定用户规模需安全评估并报告；履行算法备案 | 自用与内测规模远未达到 | 公开发布前评估 |

**（4）AI 生成内容标识**：资讯改写等生成内容标注"AI 生成 / AI 改写"及来源。

**（5）隐私说明**：即使全离线，也提供一页隐私说明：收集什么（无）、本地存什么、联网做什么、如何导出与删除。

**（6）许可证**：llama.cpp 为 MIT 许可证，须随 APK 附带许可声明；所用模型（Qwen3-VL 系列、MiniCPM 系列等）各有许可证，**以官方许可证原文为准**，发布前逐一核对是否允许再分发与商用，并在"关于"页列出。

**公开前必做清单**：数据加密；AI 身份提示与 2 小时休息提示；紧急联系人；未成年人限制方案；隐私说明；许可证声明；危机流程评估。

### 12.6 版本更新

1. 设置页"检查更新"（需联网，用户手动触发或每周一次，可关），读取一个静态版本描述文件（版本号、下载地址、SHA256、更新说明）。
2. 下载后校验 SHA256，交给系统安装器；同签名覆盖安装。
3. 数据库升级必须有迁移（已有 v1→v2 迁移范例）；每次升级前自动备份 `memory.db`。

### 12.7 发布检查清单（每个版本）

- [ ] 自检语料全过；新增 bug 均已有对应语料
- [ ] 实机验收清单全过（调试包）
- [ ] 正式包签名正确，`versionCode` 递增
- [ ] 覆盖安装旧版本后数据完整（数据库迁移通过）
- [ ] 全新安装后首启引导完整走通（含模型下载 / 导入）
- [ ] `crash.log` 为空，连续自用 3 天
- [ ] 更新说明、SHA256、许可证与隐私说明随包发布

## 十三、实施路线

> 原则：先稳后扩；每阶段有验收标准，未通过不进入下一阶段。工期为业余时间的粗略估计，以实际为准。

| 阶段 | 内容 | 验收标准 | 粗估 |
|---|---|---|---|
| **A 稳定** | M7 实机验收与修复；调试包分离；取消 / 推迟提醒 | 验收清单全过；连续 3 天无虚假承诺 | 1 周 |
| **B 性能与安装** | 前缀 KV 缓存；上下文裁剪；模型下载 / 导入与模型管理；首启引导 | 第二轮起延迟减半；新手机不用 adb 可完成安装 | 2–3 周 |
| **C 秘书完善** | 每日简报；闲忙模型与每日节奏；查询日程；资讯模块（可选联网） | 简报每天在合适时段出现；主动消息回应率较 M7 提升 | 2–3 周 |
| **D 玩伴第一层** | 游戏框架 + 第一层小游戏 + 战绩进伙伴层 + 心跳邀请 | 自检覆盖游戏规则；自用一周仍愿意玩 | 1–2 周 |
| **E 共同成长** | 记忆 v3（世界层、伙伴层、会话摘要、隐私控制）；"出发与归来"；成长手账；关系阶段 | 跨会话能回忆共同经历；人设间只通过世界日志互知 | 4–6 周 |
| **F 内测发布** | 正式签名与版本机制；合规"公开前必做"中适用于内测的部分；10–30 人内测 | 发布检查清单全过；收集到第一批反馈 | 2 周 |
| 以后 | 第二层文字冒险；云端交接 L2；人设扩充；公开侧载评估 | — | — |
