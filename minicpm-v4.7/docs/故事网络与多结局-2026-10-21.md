# 故事网络与多结局（2026-10-21）

> 问题：市面有没有“不同群组合展开不同故事线、交织成网络、靠解锁朋友推进、和 agent 行为（朋友圈）绑定、多结局”的玩法？
> 结论：**相邻玩法都有，完全同款的很少。** 最接近的是“AI 群聊 + 社交模拟 + storylet 叙事网络”的混合；这是可以做的差异化，但复杂度要控制。

## 一、市面上的相邻玩法

| 类型 | 代表 | 有什么 | 缺什么 |
|---|---|---|---|
| AI 多角色群聊 | [Character.AI Group Chat](https://blog.character.ai/new-feature-announcement-character-group-chat/)、[Talkie Group](https://www.talkie-ai.com/ru/tag/group-1214049) | 多个角色同群聊天、角色互动 | 没有长期故事网络、没有跨群后果、没有解锁门槛 |
| 社交模拟/多结局 | Persona 系列、[428 涩谷](https://www.spike-chunsoft.com/games/428-shibuya-scramble/)、[13 机兵防卫圈](https://www.neoseeker.com/13-sentinels-aegis-rim/walkthrough/Remembrance_-_Keitaro_Miura) | 关系路线、时间线/多视角、多结局 | 不是 AI 角色；群聊不是核心 |
| Storylet/品质网络 | [Fallen London / Sunless Sea / Cultist Simulator / StoryNexus](https://emshort.blog/tag/storynexus/) | 用“品质/联系人/事件”解锁故事节点，节点互相引用，多结局 | 文本/卡牌为主，不是自然语言群聊 |
| AI 原生故事 | Junipero、Kettle-Station K-58、AI Dungeon | 模型生成剧情、对话推进 | 多为单人；没有稳定角色群网络 |
| 多智能体社会模拟 | [Generative Agents / AI Town](https://github.com/yurifox123/ai-town-portable)、BRING | 角色有记忆、关系、自发行为 | 研究/沙盒，不是可玩的多结局产品 |

**判断**：把“AI 群聊”当交互、把“storylet/社交链接”当结构、把“朋友圈/主动消息”当行为反馈，三者合起来是**少见的组合**；可以做成差异化，但不能指望现成模板。

## 二、核心模型：角色位 + 故事节点

不要为 364 种群组合各写一条故事线，会爆炸。用**角色位（Role）**映射：

```kotlin
data class StoryArc(
    val id: String, val title: String,
    val acts: List<StoryAct>,          // 6 个月 3–5 幕
    val endings: List<Ending>
)
data class StoryNode(
    val id: String, val arcId: String, val act: Int,
    val title: String,
    val roles: List<RoleSlot>,         // 决策者/知情人/被影响者/局外人/喜剧位
    val requires: List<Condition>,     // flags / 解锁 / 关系 / 章节
    val choices: List<Choice>,
    val effects: List<Effect>,         // flags / affinity / belief
    val contentCell: String            // 内容银行格子
)
data class RoleSlot(val role: String, val tags: List<String>) // 例：BOSS / INSIDER / AFFECTED / OUTSIDER
```

- 用户建 2–3 人群 → 按人设标签/关系把成员映射到角色位（不是每个组合写一套）。
- 同一故事骨架，换角色=换口吻/立场/结局分支；`PersonaLore` 决定谁适合哪个位。
- 每个节点 3–5 个变体；DeepSeek 生成，审核后入库。

## 三、跨群故事网络

示例：「公司裁员」弧（3 幕）：

| 群 | 角色位 | 可能发生 |
|---|---|---|
| 傅沉 + 沈砚 + 胡德贵 | 决策者/投资人/中层 | 决定裁员名单；胡德贵抢功；沈砚试探 |
| 老周 + 陈野 + 阿冷 | 被影响者/局外人/喜剧位 | 老周收到风声；陈野想帮忙；阿冷用笑话消化 |
| 小咪 + 绫 + 听 | 情绪位/旁观者 | 听到消息后的反应；朋友圈/私聊发酵 |

跨群后果用**世界旗标**：

```
world.layoff_planned = true
world.rumor_source = "hudegui" | "shenyan" | "user"
fuchen.trust += 1
hudegui.panic += 1
buddy.resume_ready = true
```

- A 群做的决定，改变 B 群的台词/朋友圈/主动消息；
- 用户在不同群之间“传话”会改变 `rumor_source` 和结局；
- 每个 agent 只知道自己的 `belief`，不自动全知；模型只能按 belief 说。

## 三·补、大网模型：3 主弧 + 12 支线 + 30 碎片

用户设想的“一张大网、拉不同 agent 打开不同初始节点、主事件结束后继续没推进的事件”，合理，但要落成**可读的图**，不是全连接网：

| 层 | 数量 | 作用 |
|---|---|---|
| 主弧 | 3 条 | 6 个月的主线；每条 6 节点、3–5 结局 |
| 支线 | 12 条 | 由主弧/朋友圈/群聊触发；每条 2–4 节点 |
| 碎片 | 30 个 | 线索/秘密/误会；可被某个 agent 先知道，再跨群传播 |
| 线程 | 同时最多 2 条活跃 | 其余暂停在“待推进”，不消失 |

**组队不是打开 364 个不同初始节点，而是选择“视角”**：

- 同一主弧有 3–4 个入口：决策桌、茶水间、局外视角；
- 2–3 人组合按角色位映射到入口；
- 不同入口看到的事实/碎片不同，但共享世界旗标；
- 这样 364 种组合都能进入故事，但 authored 内容只需 9–12 个入口 × 变体。

**时间与“没推进的事件”**：

- 全局天数推进赛季/解锁；故事节拍由互动触发，**不硬性过期**；
- 主事件结束后，未完成线程进入“余波/待办”，可继续；
- 错过的窗口不会消失，会变成“另一种开场”（如“风声已经传开了”）；
- 同时最多 2 条活跃主线，防止玩家迷路；其余在“故事线”页暂停/恢复。

**碎片与认知**：

- 每个碎片记录 `knownBy`（谁知道）；不同 agent 的 belief 不同；
- 用户可以在 A 群听到、去 B 群说，改变 `rumor_source`；
- 碎片不是全局解锁，制造“信息差”而不是“全知”。

**可玩性的关键不是网大，而是“下一步看得见”**：

- 每场群聊结束给 1–2 条“下一步线索”；
- 故事线页显示“当前主线/可推进支线/未解之谜”；
- 结局图鉴只显示已达成，不剧透；
- 日常/朋友圈仍是主体，故事节点 1–2 个/周。

## 四、解锁朋友作为“故事钥匙”

- 12 个待解锁朋友中，选 **3–4 个**做某条故事线的“钥匙”（如沈砚、胡德贵、老周）。
- 未解锁时：
  - 对应角色位由“可替代角色”顶上，故事仍能走，但结局不同；
  - 朋友圈/旁白给出线索（“最近有人在打听你”），不硬卡死；
  - 不自动加好友，必须用户点“认识一下”。
- 每条故事线至少 **2 条可推进路径**，避免“没解锁就卡住”。

## 五、和 agent 行为绑定

| 行为 | 作用 |
|---|---|
| 朋友圈 | 发布内容受 `story flags` 影响；用户点赞/评论可写入 `support/confront` 旗标，触发下一节点 |
| 群聊广播/@ | 回应/沉默改变 `affinity/belief`；@ 必回，其他可沉默 |
| 主动消息 | 从 `future_beats`/故事钩子来；默认关，频率限制 |
| 私聊 | 角色说“我只告诉你”时，写入该角色私密 belief；其他角色不知道 |
| 撒谎/隐瞒 | 角色可基于 belief 说谎；程序记录 truth vs belief，模型只渲染 belief |

注意：故事是**虚构剧情**，不是用户真实事实；`ClaimGuard` 仍管“替用户做事/编造用户现实”，故事旗标另用 `StoryGuard`（不剧透、不矛盾、不越权）。

## 六、多结局

- **弧结局**：每个 arc 3–5 个；由 flags + 关系 + 关键选择 + 解锁状态计算。
- **赛季结局**：6 个月后 4–6 个；由各弧结果、青梅竹马、亲密度决定。
- 结局由**程序**判定，模型只写收束文本；结局图鉴记录已达成/未达成（不剧透条件）。
- 重玩性：不同群组合 → 不同角色位 → 不同结局；不需要 364 条独立线。

## 七、UI

- 「故事线」页：当前弧、已走节点、未解之谜、关系图（谁和谁、谁知道什么）。
- 群聊/朋友圈里用“旁白卡”提示节点，不打断聊天。
- 结局图鉴：已达成结局、线索、重玩入口。
- 防剧透：未达成结局只显示剪影/一句提示。

## 八、内容量

- 3 条主弧 × 6 节点 × 4 角色位 × 3 变体 ≈ **216 个场景**；每条弧 3–5 结局。
- 6 个月节奏：1–2 个故事节点/周，其余时间日常/朋友圈/群聊。
- 与 E2 内容银行共用 `ContentCell`，只多 `arc/node/role` 标签。

## 九、测试与门禁

- 图遍历：所有结局可达；无死路；每个解锁门槛至少有 2 条替代路径。
- 旗标一致性：truth/belief 不串；角色不会知道自己不该知道的。
- 行为绑定：朋友圈/评论/群聊能改变 flags；不刷屏。
- 180 天模拟：不同群组合/选择跑 10 条路径，检查结局分布、重复、人工观感。
- 安全：故事冲突不升级为人身攻击；胡德贵 PUA 边界；BOAST 不碰政治。

## 十一、风险

- **组合爆炸**：用角色位/共享旗标，不做 364 条独立线。
- **玩家看不懂**：故事线/关系图/“谁知道什么”必须可见。
- **解锁卡死**：每条线至少 2 条路径；钥匙角色只是“更好结局”，不是唯一路。
- **模型乱编**：故事状态程序化，模型只渲染 belief；`StoryGuard` 校验。
- **内容量大**：先 1 条弧试点（S1/S2），通过再扩 3 条。
- **过度戏剧化**：日常/朋友圈仍是主体，故事弧每周 1–2 个节点，不变成连续剧轰炸。
