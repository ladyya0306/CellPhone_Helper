# 方案：把模型推理放进独立进程（`:llm`）

> 状态：**待用户确认，尚未动手**（2026-10-19）。依据：《会话交接-2026-10-18》第八节的真机调查。

## 一、要解决的问题（证据见交接文档 §8.1）

| 问题 | 现状根因 | 独立进程后 |
|---|---|---|
| "无响应"（ANR） | 模型的原生内存（malloc）计入 App 进程的 ART 堆压力；主线程创建 Paint/TextView 时被强制等 GC，>5s 即 ANR（两份 ANR 栈完全一致） | UI 进程不再加载 `libai-chat.so`，原生内存不在其账上，**这条 ANR 路径消失** |
| "闪退"（被杀） | 模型常驻使整个包 RSS 3.4–5.5GB，vivo 以 LOW_MEMORY 杀进程；杀的是**唯一的进程**，UI、心跳、闹钟一起没 | 被杀的只会是 `:llm`；UI/心跳/提醒进程常驻约 100MB，不再是清理对象 |
| 闹钟被清掉 | 进程被清理时登记的闹钟一并消失 | 主进程更小、更少被清；仍需用户做后台白名单（§8.3），但不再因模型占内存而首当其冲 |
| 原生崩溃 | llama.cpp 若 SIGSEGV/abort，整个 App 一起崩 | 只崩 `:llm`，下一条消息自动重启并重载 |
| 卸载不彻底 | `cleanUp()` 后原生堆仍剩约 120MB 并被换出 | 释放 = 结束 `:llm` 进程，内存**整体**还给系统 |

## 二、总体设计

```
┌──────────── 主进程（UI / 心跳 / 提醒 / 数据库） ────────────┐        ┌──────────── :llm 进程 ────────────┐
│ MainActivity  AgentLoop  ModelLifecycle  HeartbeatService  │        │ LlmService（Bound Service）        │
│        │ 只依赖 InferenceEngine 接口（不改）               │  AIDL  │   └─ InferenceEngineImpl（原样）   │
│  RemoteInferenceEngine（新，实现 InferenceEngine）  ───────┼───────►│       └─ libai-chat.so / llama.cpp │
└────────────────────────────────────────────────────────────┘        └────────────────────────────────────┘
```

要点：

1. **接口不动**：`InferenceEngine`（`state` / `loadModel` / `setSystemPrompt` / `sendToolPrompt` / `parseToolCalls` / `cleanUp`）已经很窄。`AgentLoop`、`ClaimGuard`、`IntentRouter` 等一行不改；只把获取引擎的入口从 `AiChat.getInferenceEngine(ctx)` 换成 `RemoteInferenceEngine.get(ctx)`。
2. **AIDL 契约**（`oneway` 回调，保证流式顺序）：
   - `ILlmService`：`load(path, cb)`、`setSystemPrompt(text, cb)`、`generate(messages: byte[], tools: byte[], maxTokens, cb)`、`cancel()`、`parseToolCalls(text): byte[]`、`shutdown()`
   - `ILlmCallback`（oneway）：`onState(code, message)`、`onToken(text)`、`onDone()`、`onError(message)`
   - 载荷：prompt 通常 < 16KB，远低于 Binder 1MB 上限；token 逐个回调。
3. **状态映射**：未连接 / 已释放 ＝ `Initialized`（"可以加载"）；`LoadingModel`/`ModelReady`/`Generating` 等由 `:llm` 回调镜像；`:llm` 异常死亡 ＝ 回到 `Initialized`（**不是 Error**），在途的生成 Flow 以"推理进程被系统回收"异常结束。
4. **释放（卸载）**：`ModelLifecycle.unload` 改为解绑 + `LlmService` 在 `onDestroy` 里 `Process.killProcess(myPid)`，内存整体归还。触发时机不变：退到后台**立即**（vivo 会冻结后台进程，不能靠定时器）、`onTrimMemory`、后台一轮结束。
5. **自动重载**：用户在模型缺失时发消息，`sendMessage` 先触发加载（现在只在 `onStart`/`onCreate` 触发）；加载期间确定性指令照常可用。
6. **进程隔离细节**：`App.onCreate` 会在两个进程都执行，`onTrimMemory` 里的卸载逻辑加进程名判断；`:llm` 只读模型文件、只写 `boot.log`，不碰数据库与待办。

## 四、测试与验收（"完成"必须附证据）

**先写用例（JVM，纯 Kotlin，沿用 `selftest-jvm.ps1`）**：用假的 `LlmTransport` 验证代理逻辑——
加载时的状态转移（Initialized→LoadingModel→ModelReady）；生成时 token 按序到达；`:llm` 中途死亡 → Flow 抛出明确异常且状态回到 `Initialized`；收集方取消 → 向服务发 `cancel`；`release()` 后状态为 `Initialized` 且再次 `loadModel` 可重新连接；并发 `loadModel` 只触发一次连接。

**真机验收**（逐条附命令输出）：

| # | 验收项 | 通过标准 |

## 五、风险与取舍

| 风险 | 说明 | 对策 |
|---|---|---|
| 首次调用多 ~0.5s | 需要拉起 `:llm` 并加载 so | 加载本就要 13s，可忽略 |
| Binder 回调乱序 | 流式 token 经 IPC | `oneway` 调用同一 Binder 内按序；用例 2 覆盖 |
| `:llm` 被杀后的体验 | 当前一轮失败 | 明确提示 + 自动重载；确定性指令不依赖模型 |
| 后台启动限制 | Android 对后台启动服务有限制 | 只在前台 Activity 可见时绑定；心跳、提醒不使用模型，不受影响 |
| 仍不能保证夜间闹钟 | 取决于 vivo 对**包**的清理策略（`single-cleaner` 曾杀过仅 91–208MB 的本应用进程） | 本方案降低概率但不能消除；必须配合 §8.3 的系统设置；用验收 #7 实测 |

## 六、需要你确认的三点

1. **后台策略**：退到后台**立即**释放模型（推荐；每次回来约 13 秒重载），还是在后台保留（回来秒开，但 3.4GB 常驻会让系统更倾向清理本包）。默认建议前者，之后可做成设置项。
2. **释放方式**：直接结束 `:llm` 进程（推荐，内存整体归还）。
3. **范围**：本次**不**改 `lib`/C++、**不**动调试包/正式包分离（需要新包名，另行确认）。
