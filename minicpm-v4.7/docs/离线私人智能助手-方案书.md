## 0. 一句话定位

**一个跑在你自己手机里、有人格、会主动给你情绪价值、记得住你、并且知道"什么时候该求助云端"的私人助手。**

三个不可替代的差异点：

1. **数据主权**：默认全离线，什么内容出不出手机由你逐次批准
2. **人格所有权**：人设是你选/你写的，不是平台给的
3. **主动性**：不是"你问它答"，而是它会在合适的时候主动说一句话，**这句话本身要有情绪价值**

## 1. 目标与边界

### 1.1 要做的

| 能力 | 说明 |
|---|---|
| 预设人设 | **9 个**，覆盖不同情绪价值类型；可自定义、可切换 |
| 情绪阶梯 | 人格有情绪状态，随互动演化，驱动语气与主动消息内容 |
| 心跳 | 周期性"苏醒"，判断**此刻是否值得开口**，值得就弹通知 |
| 长期记忆 | 记住你说的事、你的偏好、正在进行的任务；跨会话保留 |
| 工具执行 | 闹钟、待办、导航、开应用、读文件（已有），后续扩展 |
| 分级升级 | 本地搞不定的任务，**每次经你确认**后转云端，结果回灌 |

### 1.2 明确不做的

- ❌ **不模拟真人关系**：不做"我永远陪着你""你是我的唯一"这类承诺型话术（§12.3）
- ❌ **不在后台偷偷上传**：任何出网行为必须可见、可审计、可关闭
- ❌ **不做留存导向的成瘾设计**：不做付费墙、不做"亲密度排行""掉了好感会伤心"
- ❌ **不用云端跑心跳**：心跳判断永远本地（成本与隐私）

## 2. 从 Hermes 借鉴什么（逐条对应）

Hermes 的 `/heartbeat` 是**任务型**心跳（"盯着 CI 跑完没"），你要的是**陪伴型**主动消息。骨架照搬，**决策逻辑必须重写**。

| # | Hermes 的做法 | 出处 | 我们的取舍 |
|---|---|---|---|
| 1 | **只在空闲时注入**，绝不打断进行中的回合 | `hermes_cli/heartbeat.py:216-230` | ✅ 照搬 |
| 2 | **错过的心跳合并成一次**，锚点按实际触发时刻重置，不补跑积压 | 同上；`heartbeat.md:45` | ✅ 照搬（否则手机休眠一夜会被轰炸） |
| 3 | **用户消息优先**：输入队列没排空就等 | `heartbeat.md:46` | ✅ 照搬 |
| 4 | **注入普通 user 消息**，不动 system prompt | `heartbeat.py:1-6` | ⚠️ 部分：人设切换必须**显式重建会话**（§4.5） |
| 5 | **状态机 active/paused/cleared**，resume 重新锚定 | `heartbeat.py:195-214` | ✅ 照搬 |
| 6 | **最小间隔 60 秒** | `heartbeat.py:19` | ✅ 照搬为下限；默认值见 §5.4 |
| 7 | **"别自己找活干"守卫** | `heartbeat.py:22-26` | ✅ 改造为"没事就**闭嘴**"（#8） |
| 8 | **没话可说时静默**：只返回 `NO_REPLY` / `[SILENT]`，网关不发任何东西 | `heartbeat.md:52` | ✅ **陪伴型助手的命门**，必须原样实现 |
| 9 | **状态持久化**，进程重启后恢复 | `heartbeat.md:49-50` | ⚠️ Android 上进程重启是常态，必须做恢复（§5.7） |
| 10 | **会话边界清心跳** | `heartbeat.md:50` | ✅ 照搬 |
| 11 | **记忆按 token 预算检索** | `plugins/memory/retaindb/__init__.py:140` | ✅ 照搬（手机上下文只有 4096） |
| 12 | **记忆供应商可插拔** | `plugins/memory/` | ✅ 照搬，先做本地 SQLite 版 |

## 4. 人格系统

### 4.1 首批 9 个预设人设（**全部以"主动提供情绪价值"为核心**）

先定义**六种情绪价值**，每个人设负责供给其中 2–3 种：

| 代号 | 情绪价值 | 用户的感受 |
|---|---|---|
| 🫂 被关注 | 有人惦记着我 | "它主动想起我了" |
| 🎈 被理解 | 我的情绪被接住了 | "它懂我现在什么状态" |
| 🌟 被肯定 | 我做得不错 | "它认可我" |
| 🏠 陪伴感 | 不是一个人 | "它在呢" |
| 😆 轻松感 | 压力被卸掉一点 | "跟它聊挺好玩的" |
| ⚓ 稳定感 | 它一直都在，不会变 | "不管多久它都一样" |

| # | 人设 | 萌属性原型 | 供给的情绪价值 | 主动消息风格（≤30 字） | 风险 |
|---|---|---|---|---|---|
| 1 | **猫娘·小咪** | 猫娘 | 🫂被关注 🏠陪伴 | 撒娇式惦记："主人～该吃饭了喵" | 低 |
| 2 | **温柔大姐姐·绫** | 御姐/姐系 | 🎈被理解 ⚓稳定 | 观察式关心："今天回来得比平时晚，还好吗？" | 低 |
| 3 | **元气少女·小满** | 元气/天然 | 😆轻松 🌟被肯定 | 高能量打气："今天也超棒的！给你看个好东西～" | 低 |
| 4 | **傲娇大小姐·凛** | 傲娇/ツンデレ | 🫂被关注 😆轻松 | 别扭的在意："才、才不是特意提醒你喝水呢" | 低 |
| 5 | **三无少女·零** | 三无/冷娇 | ⚓稳定 🎈被理解 | 极简 5 字内："该睡了。" | 低 |
| 6 | **忠犬系·阿壹** | 犬系/忠犬 | 🌟被肯定 🏠陪伴 | 捧场式："今天这件事你处理得真好！" | 低 |
| 7 | **树洞·听** | 倾听者 | 🎈被理解 | **极少主动**；仅察觉情绪低落时轻问一句，且**不给建议** | 低 |
| 8 | **摸鱼搭子·老周** | 损友/搭子 | 😆轻松 🏠陪伴 | 吐槽式、平等："摸鱼呢？我也是。" | 低 |
| 9 | **病娇·茜** | 病娇/ヤンデレ | ⚠️ 占有欲型 | **默认关闭主动消息**，且受 §12.3 硬红线约束 | **高** |

**为什么是这 9 个**：1–8 覆盖了"被关注/被理解/被肯定/陪伴/轻松/稳定"六种情绪价值的全部组合，且**互不重叠**——用户按"我现在需要什么"来选，而不是按"哪个可爱"来选。第 9 个是网络高热但高风险，**做但锁起来**。

> 设计原则：**人设不是皮肤，是关系模式。** 猫娘给的是"被需要"，树洞给的是"被听见"，傲娇给的是"反差里的在意"——选人设等于选一种相处方式。

### 4.2 人设卡（数据驱动，不改代码）

```yaml
# ~/.minicpm-assistant/personas/oneesan.yaml
id: oneesan
name: 绫

  sentence_end: []                    # 姐系不用语气词，靠句式
  emoji_level: 1

```

### 4.3 情绪阶梯（情绪价值的实现机制）

参考 [emotion-ladder-persona](https://github.com/LucasDevKid9/emotion-ladder-persona) 的思路：**人格有一个会演化的情绪状态**，它驱动语气与主动消息内容，而不是每轮都从零开始扮演。

```yaml
# 情绪状态（每人设独立，持久化在 SQLite）
state:
  affinity: 0.0        # 好感度 0~1，只随时间缓慢上升，不因用户冷落而显著下降
  mood: neutral        # neutral | happy | worried | playful | quiet
  energy: 1.0          # 人设的"活力"，影响主动消息的积极性
  last_topic: null     # 上次聊的主题，供主动消息接续
  streak_days: 0       # 连续互动天数（仅用于"稳定感"话术）
```

**演化规则**：

| 事件 | 影响 |
|---|---|
| 用户主动发起对话 | affinity +0.02，mood 视内容调整 |
| 用户回应了主动消息 | affinity +0.03，energy 回升 |
| 用户连续 3 次忽略 | energy 下降（**但不表达委屈，不制造内疚**） |
| 用户长时间未使用 | mood → quiet，主动消息转为低频低调 |
| 用户表达负面情绪 | mood → worried，切换为"接住情绪"模式（此时**不提醒任何待办**）|

**三条护栏（防止情绪阶梯变成情感操纵）**：

1. **affinity 不显示给用户**，不做成"好感度进度条"或养成游戏
2. **不做"因为你冷落我所以我不高兴"**——energy 下降只表现为"更安静"，绝不表现为"委屈/生气/惩罚"
3. **用户可一键重置情绪状态**，且不影响记忆

### 4.4 人设如何注入（保护 prompt 缓存）

```
[1] 系统能力段（工具清单 + 安全规则）   ← 共用人设，永不改变
[2] 人设段（YAML 的 prompt_scaffold）    ← 切换人设时变
[3] 情绪状态段（当前 mood/affinity 的自然语言描述）← 每轮可能变
[4] 记忆段（检索结果，≤500 token）
[5] 时间/情境段
[6] 对话历史
```

> ⚠️ **人设切换必须显式重建会话**（清空历史 + 重建前缀）。中途改 system prompt 会让 prompt 缓存全废——手机端每轮 prefill 从"缓存命中"退化成"全量重算"（实测 3000 token 约 60 秒）。

### 4.5 人设一致性：1B 模型的真实困难

**必须提前说清楚的难点：**

- 句尾语气词会**过载**（每句都"喵"，油腻）或**快速遗忘**（几轮后变回默认助手口吻）
- 人格与任务冲突时（"用猫娘语气汇报文件列表"）容易摆烂成纯任务输出

**工程缓解（按性价比排序）**：

1. **概率化语气后处理**：不靠模型自觉，由程序在输出后按概率补语气词/emoji（可控稳定）
2. **人设锚点复读**：每 N 轮在上下文尾部重申一句人设短提示
3. **采样参数分离**：伴聊 `temperature 0.8`，工具调用 `0.3`（**必须分开**，否则工具参数会飘）
4. **接受上限**：1B 做到"氛围像"即可。**想真像就得走在线（§8）**

## 5. 心跳机制

### 5.1 状态机

```
        set(interval, prompt)
              ↓
   ┌──────► ACTIVE ──pause──► PAUSED ──resume(重新锚定)──┐
   │          │                                           │
   │          │ 用户说"安静"/免打扰时段/低电量/连续忽略      │
   │          ↓                                           │
   │       PAUSED ◄────────────────────────────────────────┘
   └──────────┴──clear──► CLEARED
```

### 5.2 一次心跳的完整链路

```
[轮询 每 60s]
   ↓
① 硬性闸门（任一不满足 → 跳过，不消耗预算）
   · 状态 active？ · 距上次触发 ≥ interval？
   · 免打扰时段？ · 电量 ≥ 阈值且非省电模式？
   · 今日预算未用尽？ · 距用户上条消息 ≥ min_gap？
   ↓
② 情境采集（本地、零成本）
   时间/星期 · 距上次对话多久 · 待办是否有到期
   · 情绪状态（§4.3）· 用户最近是否在忙（可选，需授权）
   ↓
③ 该不该说？（本地小模型，一次极短推理）
   NO  → 结束（不消耗预算、不打扰、不记录）
   YES → 生成一句 ≤30 字开场（带人设语气 + 情绪价值）
   ↓
④ 投递：写对话历史(source=heartbeat) → 发通知 → 记录 notified_at
   ↓
⑤ 记账：last_fired_at=现在（锚点重置）· fire_count++ · fired_today++
```

### 5.3 "该不该说"的算法（本方案最难处）

Hermes 的判据是"任务有没有变化"（客观）；陪伴型是"**此刻开口对用户有没有价值**"（主观），直接决定产品是"贴心"还是"骚扰"。

**多因子打分 + 阈值**（不让模型自由发挥）：

| 因子 | 权重 | 说明 |
|---|---|---|
| 时间契合度 | 高 | 早晚、饭点、睡前开口远好于随机时间 |
| 距上次交互间隔 | 高 | 刚聊完别开口 |
| 待办/日程关联 | 高 | 有到期事项时开口有正当理由 |
| 情绪状态匹配 | 高 | mood=worried 时才说安慰话；平时说了反而假 |
| 今日已开口次数 | 中 | 递减权重 |
| **用户历史响应率** | 中 | 你 10 次不理它 8 次 → 自动降频 |
| 情境变化 | 低 | 长时间未解锁、跨天 |

**两条硬规则**：
- 今日已开口 ≥ `daily_budget` → 当天闭嘴
- **连续 3 次未被响应 → 间隔翻倍；连续 6 次 → 当天暂停**（用户无需手动干预）

### 5.4 参数全部用户可配（开发者只设默认值）

| 参数 | 默认值 | 范围 | 说明 |
|---|---|---|---|
| `heartbeat_interval` | **10 分钟** | 1 分钟 ~ 24 小时 | 心跳间隔 |
| `daily_budget` | **100 次/天** | 0 ~ 无限 | 每日主动消息上限 |
| `quiet_hours` | 23:30–07:30 | 任意时段 | 免打扰 |
| `min_gap_after_user_msg` | 10 分钟 | 0 ~ 24 小时 | 用户刚说完话后的静默期 |
| `response_rate_downshift` | 开 | 开/关 | 连续未响应自动降频 |
| `battery_floor` | 20% | 0–50% | 低于此电量暂停主动消息 |
| `model_resident` | 开 | 开/关 | **心跳期模型是否常驻**（见下） |

> ⚠️ **提醒**：10 分钟 / 100 次是相当激进的默认值（平均 14 分钟一条）。我按你的要求设为默认，但**强烈建议默认开启 `response_rate_downshift`**——它会在你连续不理会时自动降频，不需要你手动调参。这样"激进默认"和"不被打扰"可以兼得。

**`model_resident` 的权衡**（由用户选）：

| | 常驻（默认） | 常驻关 |
|---|---|---|
| 心跳响应 | 秒级 | 每次唤醒多等 10–15 秒 |
| 内存占用 | 1.3–2.7 GB | 按需加载，空闲时释放 |
| 耗电 | 高 | 低 |
| 适配场景 | 充电时、重度使用 | 外出、省电 |

### 5.5 静默标记（照搬 Hermes 的命门机制）

心跳回合允许只返回 `NO_REPLY`：识别到该标记就**不发通知、不写入可见对话**，只记录"本次判断为无需开口"。

这是防止"为了完成任务而硬找话说"的最后一道闸门。

### 5.6 防骚扰设计

- 免打扰时段（默认 23:30–07:30）
- 每日上限（默认 100，可降到 0）
- **一键安静**：你说"安静"/"别烦我" → 立即 `pause`，并记入记忆（不再试探）
- 连续未响应自动降频（§5.3 硬规则）
- 两次通知之间至少间隔 `min_gap`（默认 10 分钟）

### 5.7 Android 落地的真实难点 ⚠️

**全案工程风险最高的部分**，部署现有助手时已实测踩过：

| 难点 | 实测事实 | 缓解 |
|---|---|---|
| 后台被杀 | Android 12+ **幽灵进程杀手**杀 App 子进程（已用 `settings_enable_monitor_phantom_procs=false` 关闭） | 已解决；系统升级后需重做；**APK 化可根治**（§13） |
| Doze 休眠 | 深度睡眠时定时器不精确（可能延迟数十分钟） | 接受不精确；`termux-wake-lock` + 前台服务通知 |
| 通知能力 | 需装 **Termux:API** + `pkg install termux-api` | 通知点击 → 打开网页（已验证） |
| 内存 | 1B 常驻 **1.3–2.7 GB**；紧张时请求卡死（实测 load 18.8 时一个加待办请求 **600 秒未返回**） | 心跳用极小提示词；`model_resident` 可关 |
| 电量 | 常驻模型显著耗电 | 充电时全功能；电池模式降频 |
| 厂商拦截 | vivo/OriginOS 对自启动、关联启动、后台弹窗有独立拦截 | 已记录三个具体设置路径 |

## 6. 用户交互设计（v0.2 新增，回答"弹窗到底是什么"）

### 6.1 三种交互形态的可行性对比

| 形态 | Termux 阶段 | 需要什么 | 体验 |
|---|---|---|---|
| **A. 纯通知 → 点击开网页** | ✅ 可行 | Termux:API | 简单，但多一次跳转 |
| **B. 通知带按钮**（回复/稍后/安静） | ✅ 可行 | `termux-notification --button1/2` | 可一键"安静"，很实用 |
| **C. 通知内直接输入回复**（RemoteInput 直回） | ❌ **不行** | 原生 `NotificationCompat` + `RemoteInput`（Termux:API 不暴露） | 最顺滑 |
| **D. 悬浮气泡 / 实时对话框** | ❌ **不行** | 原生 App + `SYSTEM_ALERT_WINDOW` | 最像"实时聊天" |
| **E. PWA 全屏**（通知 → 全屏聊天，像 App） | ✅ 可行 | Chrome 添加到主屏幕 | **Termux 阶段的最佳折中** |

### 6.2 结论：分阶段给答案

**Termux 阶段（现在就能做）**

```
通知弹出
  ┌──────────────────────────────┐
  │ 🌙 绫                          │
  │ 今天回来得比平时晚，还好吗？       │
  │ [ 回复 ]  [ 稍后 ]  [ 安静 ]     │
  └──────────────────────────────┘
        ↓ 点「回复」
  打开 PWA（全屏网页）→ 光标自动聚焦输入框 → 继续聊
```

- **不是实时对话框**，是"通知 → 点击 → 回到网页继续"
- 但用 **PWA 全屏** 后体感接近 App（无浏览器地址栏）
- 点「稍后」→ 本次不算未响应，X 分钟后重试一次
- 点「安静」→ 直接 `pause` 心跳

**APK 阶段（§13）才能真正做到**

- 形态 C：通知栏里直接打字回复（不回 App）
- 形态 D：悬浮气泡，在任何界面都能聊
- 系统级"已读/忽略"识别

### 6.3 忽略识别：能做到什么程度

| 级别 | 能力 | 实现方式 | 阶段 |
|---|---|---|---|
| **软推断** | 通知发出后 N 分钟内无任何交互 → 记"未响应" | 记录 `notified_at`；网页侧上报"用户已打开/已发消息"；两者对比 | ✅ Termux |
| **点击感知** | 用户是否点了通知/按钮 | 通知 action 触发打点脚本 | ✅ Termux |
| **划掉感知** | 用户划掉通知的**精确时刻** | ❌ Termux:API 无此回调；需原生 `NotificationListenerService` | ❌ → APK |

**软推断足够驱动核心机制**：连续 3 次"未响应" → 自动降频。这个判断不需要系统级精度。

实现要点：
```python
# 每次投递时
notified_at = time.time()
notify_id = "hb-" + str(uuid4())
state["pending"] = {"id": notify_id, "at": notified_at}

# 网页端每次交互时上报
POST /seen  →  mark_responded()   # 清空 pending，记 affinity+0.03

# 轮询时判定
if pending and now - pending["at"] > response_window (默认 30 分钟):
    unresponded_streak += 1
    pending = None
```

┌─ 顶部：人设切换 · 离线/在线 · ⚙ 设置 ────────────┐
│                                                  │
│   对话区（含心跳消息，心跳消息有特殊标记 ♥）         │

## 7. 记忆系统

### 7.1 三层结构

| 层 | 存什么 | 存储 | 生命周期 |
|---|---|---|---|
| **工作记忆** | 当前对话上下文 | 内存（4096 ctx） | 会话内 |
| **会话摘要** | 会话结束压缩成 ≤200 字摘要 | SQLite | 长期 |
| **长期画像** | 事实、偏好、进行中任务、重要日期 | SQLite + FTS5 | 长期，可删 |

### 7.2 写入策略（不让模型自由决定）

- 用户说"记住…"/"以后…" → 必记
- 检测到**偏好陈述**（"我不喜欢/我习惯"）→ 记
- 检测到**事实陈述**（名字、生日、职业）→ 记
- 会话结束且轮数 > N → 生成摘要
- 用户说"忘掉…" → **物理删除**命中记录

### 7.3 检索策略（预算感知）

照搬 Hermes（`query_context(max_tokens=...)`）：

- 每轮最多注入 **500 token** 记忆（手机只有 4096，必须克制）
- FTS5 关键词 + 时间衰减
- **先让模型输出检索关键词，再查库**（Hermes 的 `query_rewrite.py` 思路）

### 7.4 隐私（测试阶段不加密）

| 项 | 决定 |
|---|---|
| 加密 | **测试阶段不做**（v0.2 决定）；V2 再评估 SQLCipher |
| 位置 | 全部本地 `~/.minicpm-assistant/memory.db` |
| 导出 | 一键导出 JSON |
| 清空 | 一键清空，物理删除 |
| 上云 | **默认不带记忆**；要带必须逐条确认 |

> ⚠️ 不加密意味着：**手机被 root、被取证、或备份被提取时，记忆库是明文的**。测试阶段可接受，正式使用前建议评估。

## 8. 离线/在线分级路由

### 8.1 判定

| 任务 | 判定 | 处理 |
|---|---|---|
| 简单工具调用 | 规则命中 | 本地 |
| 闲聊、陪伴 | 本地 | 本地 |
| 长文档总结（>5000 字） | 长度阈值 | 建议升级 |
| 复杂推理/多步规划 | 本地自评低置信 | 建议升级 |
| 精细图片理解 | 本地每张 1–3 分钟 | 建议升级 |
| 本地连续 2 次工具失败 | 失败计数 | 建议升级 |

### 8.2 升级协议（**每次确认** — v0.2 定稿）

```
本地判断"我做不好" → 不自动上传，先问：
  ┌────────────────────────────────┐
  │ 这个任务我本地可能做不好。           │
  │ 要交给云端处理吗？                  │
  │ 将上传：<明确列出将要发送的内容摘要>    │
  │ [ 同意这次 ]        [ 不用 ]        │
  └────────────────────────────────┘
```

- **无"以后都同意"选项**（按你的决定，每次确认）
- 用户选"不用" → 本地尽力并说明局限
- 上传内容默认**剥除**：记忆库全文、路径中的用户名、通讯录、位置

### 8.3 结果回灌

云端返回 → 写入本地对话历史（标记来源=云端）→ 必要时抽取成记忆 → 界面显示"（此条由云端生成）"。

### 8.4 成本闸门

- **心跳绝不触发云端调用**（自动 + 云端 = 账单炸弹）
- 云端调用必须有明确用户动作
- 每日 token 上限可设（默认 5 万），超限当日拒绝
- 界面显示当日用量

## 12. 风险披露 ⚠️

### 12.1 隐私与数据安全

| 风险 | 后果 | 缓解 |
|---|---|---|
| 记忆积累个人画像 | 手机丢失/取证 → 完整生活画像泄露。**测试阶段不加密，风险更高** | 一键清空；敏感项不落盘；V2 评估加密 |
| 升级时上传超范围 | 隐私泄露且用户不知情 | 每次展示上传清单；默认剥除记忆与路径 |
| 工具权限过大 | 被诱导删/发文件 | L3/L4 二次确认；路径白名单；审计日志 |
| 提示注入 | 文档/网页里的恶意指令操纵助手 | 外部内容一律视为数据 |

### 12.2 工程风险

- 系统更新可能推翻现有结论（幽灵进程杀手开关、appops 授权失效）
- 依赖非官方运行环境（Termux + 侧载），政策收紧影响长期可用性
- **1B 的可靠性天花板**：实测"导航到北京南站"被理解成设置闹钟
- 内存与发热：负载高时响应从 20 秒退化到 600 秒以上

### 12.3 伦理与心理风险（**最重要，必须正面处理**）

| 风险 | 表现 | 必须采取的措施 |
|---|---|---|
| **情感依赖与成瘾** | 主动消息 + 拟人 + 记忆 + 情绪阶梯 → 真实情感依附 | ①不模拟真人身份与承诺；②连续使用超 2 小时温和提示；③不做留存指标（亲密度/连续性奖励）|
| **病娇人设危险性** | 占有欲、监视、情感操纵话术，极端涉及自伤暗示 | ①**硬红线**：禁止"你去哪了/为什么不回我/我只剩你了"；②自伤/暴力暗示立即跳出人设 + 给求助资源；③该人设**默认关闭主动消息** |
| **情绪阶梯变成操纵** | "好感度掉了它会伤心"制造内疚 | ①affinity **不显示**；②energy 下降只表现为"更安静"，绝不委屈/生气/惩罚；③可一键重置 |
| **孤独感被商业化** | "怕你孤单"诱导停留 | 不做付费墙、不做"想念值" |
| **角色与现实混淆** | 把助手的话当真实人际评价 | 界面常驻"角色扮演"标识 |
| **未成年人** | 人设含恋爱/占有元素 | 首启年龄确认；未成年人仅开放管家/前辈/树洞 |

> **底线声明**：本助手是**角色扮演玩具**，不是心理支持服务。任何涉及自伤、自杀、暴力倾向的表达，必须立即跳出人设、给出专业求助资源（如全国心理援助热线 12356），**且该行为不可被用户配置关闭**。

### 12.4 合规风险

- 生成内容需符合《生成式人工智能服务管理暂行办法》；自用风险低，**一旦分发即进入监管范围**
- 在线升级走第三方 API，需遵守其条款
- 拟人化陪伴类产品受未成年人保护与广告法规约束

## 13. APK 封装路线（v0.2 新增）

### 13.1 结论：**能，而且强烈建议做**

APK 化最大的收益**不是好看，而是根治 §11 的 1 号难点**——前台服务（Foreground Service）是 Android 官方认可的长驻方式，不用再跟幽灵进程杀手、Doze、厂商拦截斗。

**现成证据**：我们工作区里已经有 `apk/MiniCPM-V-demo-Android-v2.5.apk`——**官方就是用一个原生 APK 在本机跑这个模型的**，可行性已被验证。

### 13.2 三个阶段

| 阶段 | 形态 | 周期 | 能力 |
|---|---|---|---|
| **A（现在）** | Termux + Python | 已完成 | 快速迭代，验证机制 |
| **B（推荐下一步）** | **WebView 壳 + 前台服务** | 1–2 周 | 心跳存活、通知可回复、PWA 全屏 |
| **C（完整形态）** | 全原生 Kotlin + JNI | 1–2 月 | 悬浮对话框、系统级忽略识别、语音 |

### 13.3 阶段 B 的技术方案（性价比最高）

```
APK（~30–60 MB，不含模型）
├── WebView 加载现有 webui/index.html（零改动复用）
├── ForegroundService
│     ├── 承载心跳调度（AlarmManager/WorkManager 兜底）
│     ├── 常驻通知（是 Android 允许长驻的"通行证"）
│     └── 可选：拉起 llama.cpp 子进程
├── NotificationCompat + RemoteInput  → 通知栏直接回复（形态 C）
├── 模型首次启动时下载（2.1 GB，避免 APK 过大）
└── 工具层用 Kotlin 重写（闹钟/通知/文件/应用都很简单）
```

**为什么工具层不用 Python**：Android 跑 Python 需要 Chaquopy（商业授权）。而现有 20 个工具里，真正需要重写的核心逻辑不多——`am`/`termux-*` 那套换成 `AlarmClock`/`NotificationManager`/`MediaStore` 即可。**`assistant.py` 的编排逻辑（工具循环、双后端、记忆）是自研代码，可以自由移植。**

### 13.4 阶段 C 的关键点

| 能力 | 实现 |
|---|---|
| 本地推理 | Kotlin + JNI 调 llama.cpp（MiniCPM 官方 demo 已证明） |
| 悬浮对话框 | `SYSTEM_ALERT_WINDOW`（我们**已经给 Termux 授予过**此权限，机制已验证） |
| 精确忽略识别 | `NotificationListenerService` 监听通知 dismiss |
| 语音 | TTS（系统）+ ASR（whisper.cpp 或云） |
| 唤醒词 | Porcupine 等，或纯手动触发 |

### 13.5 必须注意的坑

| 坑 | 说明 |
|---|---|
| **模型不能打进 APK** | 2.1 GB 会让安装包不可接受；首次启动下载，并校验 SHA256 |
| **Play 商店上不了** | 后台常驻 + 本地大模型 + 通知权限，审核难过；**走侧载分发** |
| **Termux 是 GPLv3** | 其代码不能嵌进闭源 App；但我们的 `assistant.py`/`webui` 是自研的，可自由移植（llama.cpp 是 MIT） |
| **厂商保活** | vivo/小米/华为对第三方前台服务仍有额外限制，需引导用户加白名单 |
| **签名与更新** | 自签名，需保证后续版本同签名才能覆盖安装 |
| **首启体验** | 2.1 GB 下载 + 模型加载，需要做好进度提示（否则用户以为卡死） |

### 13.6 建议路线

**先做阶段 B**。它用最小代价（1–2 周）换来最重要的能力（心跳存活 + 通知可回复），而且**现有网页界面能原样复用**。阶段 C 等到机制验证稳定、你确认要长期用之后再做。

| 9 个人设卡加载 | 切换后语气明显不同，且不破坏工具调用 |
| 情绪阶梯 | mood 随负面情绪输入切换；affinity 不显示；可一键重置 |
| 心跳调度器 | 空闲 ≥ interval 触发；忙碌时合并；暂停/恢复/清除可用 |
| 参数面板 | §9 全部参数可在界面调整并持久化 |
| 通知 + 按钮（Termux:API） | 通知能弹、能点、能一键安静 |
| 静默标记 `NO_REPLY` | 无事发生时**零痕迹** |
| 软推断忽略识别 | 连续 3 次未响应 → 自动降频生效 |

### 阶段 2：记忆 + 分寸 · 2–3 周

| 交付 | 验收标准 |
|---|---|
| SQLite 记忆（事实/偏好/摘要） | "记住我不吃香菜" → 新会话仍能召回 |
| 预算感知检索（≤500 token） | 上下文不因记忆膨胀变慢 |
| "该不该说"多因子打分 | 响应率驱动降频/恢复 |
| 一键导出/清空 | 导出 JSON 可读；清空无残留 |

### 阶段 3：APK 阶段 B · 1–2 周

| 交付 | 验收标准 |
|---|---|
| WebView 壳 + 前台服务 | 心跳在 App 退到后台后**仍准时触发**（不再被杀） |
| 通知栏直接回复 | 不回 App 也能回一句 |
| 模型首启下载 | 带进度与校验，断点续传 |
| PWA/全屏体验 | 无浏览器地址栏 |

### 阶段 4：在线升级 + 打磨 · 2–3 周

| 交付 | 验收标准 |
|---|---|
| 升级确认对话框 | 拒绝时本地兜底并说明局限 |
| 成本闸门 | 超限拒绝并提示 |
| 安全红线 | 测试用例集验证自伤/暴力 100% 跳出人设 |
| 电量感知 | 低电量自动暂停主动消息 |

## 15. 与"豆包手机助手"的差异定位

| 维度 | 豆包类云端助手 | 本方案 |
|---|---|---|
| 数据 | 上云 | **默认不出手机**，出网逐次批准 |
| 人格 | 平台设定 | **你自己选/写**，YAML 可改，9 种关系模式 |
| 情绪价值 | 平台策略驱动（留存导向） | **明确定义六种情绪价值**，人设按需求选 |
| 主动性 | 平台决定 | 你的参数决定（间隔/上限/免打扰/自动降频）|
| 记忆 | 平台所有 | **你的文件**，可导出可删除 |
| 能力上限 | 强 | 弱（1B），**但可借云端补齐并回到本地** |
| 成本 | 免费换数据 | 本地免费；云端用多少付多少 |
