## 一、问题诊断

### 1.1 "说办了却没办"：不是关键词漏了，而是架构把"做没做"的解释权交给了模型

旧架构中，用户最终看到的"已经设好了"是**模型的自由文本**；程序只在事后用关键词打补丁。五个独立根因：

| # | 根因 | 证据 |
|---|---|---|
| A | **守卫只在"动作类请求"时生效**。`AgentLoop` 只有当用户原话含"闹钟/待办/提醒我"等 13 个词时才检查；闲聊轮的虚假承诺全部放行 | 真实库第 63–71 条：用户只说"我喜欢喝冰美式""我习惯11点睡"，模型连续 5 次说"小咪已经帮你设了11点的闹钟"，实际没有任何工具调用 |
| B | **承诺在结构上无法兑现**。"提醒我明天三点开会"只会存一条带文字截止时间（`due="明天下午三点"`）的待办，全工程没有任何到点触发机制 | 第 9、26、75 条："小咪记得提醒你""一定准时提醒你"——永远不会发生 |
| C | **工具的"成功"不等于效果**。闹钟工具在 `startActivity()` 返回的瞬间就报"已成功设置……已经出现在系统时钟里"，并未核实；`SET_ALARM` 只能设"下一次出现的 HH:MM"，"后天7点"会被静默设成下一个7点；vivo 的"应用跳转确认"会拦截 Intent 而不抛异常；日历只写了 `HAS_ALARM=1` 却没插 `Reminders` 行，日历实际不会提醒；待办写文件失败被吞掉，照样回答"已加入" | `Tools.kt`、`TodoStore.saveRaw()` |
| D | **上下文在"教"模型撒谎**。历史里只存了 assistant 的"已经加好了"，没有存工具调用痕迹；模型从上下文学到"有人提要求 → 回一句已办好"就是正确格式 | 第 43–55 条回复越来越像复读机，且都声称已办 |
| E | **一轮对话会被中途取消**。对话协程挂在 Activity 的 `lifecycleScope`，并在 `onStop()` 里 `cancel()`。用户发完消息切去别的 App（或闹钟 Intent 把时钟/vivo 跳转确认弹到前台），这一轮就被取消：工具可能没执行、结果没落库、输入框一直禁用 | `MainActivity.onStop()` |

**结论**：在 4B 模型上，"该调工具没调""调了参数编错""没调却说调了"是常态，靠提示词和关键词补丁永远补不完。必须改成"**程序说事实，模型说情绪**"。

### 1.2 会话管理与人格切换

| 问题 | 根因 | 证据 |
|---|---|---|
| 换人设后人格串味 | 全库只有一个 `conversation_id='default'`，切到傲娇大小姐后，猫娘的历史照样作为上下文喂进去 | 第 59–71 条：傲娇大小姐自称"小咪"、喊"主人"、句尾带"喵" |
| 换人设要等 30–40 秒 | 为绕开 `setSystemPrompt` 只能调用一次的限制，每次换人设都卸载并重载 2.4GB 模型 | APK 工程方案 §9.3 |
| 心跳污染上下文 | 心跳模板消息以 assistant 身份落库，并作为对话轮次喂给模型；10 分钟一条时，6 条历史里可能全是模板 | 第 10–17 条连续 8 条心跳 |
| 返回键后再打开必然"模型加载失败" | `onDestroy()` 调用 `engine.destroy()` 销毁了**进程级单例**；心跳前台服务让进程一直存活，再次打开拿到的是已销毁的实例 | `MainActivity.onDestroy()` + `InferenceEngineImpl.getInstance()` |
| 一次 prompt 失败后永久不可用 | `sendToolPrompt` 在 `processRawPrompt` 失败时直接 `return`，状态停在 `ProcessingUserPrompt`，之后每轮都因状态检查失败 | `InferenceEngineImpl.kt` |

**一个被误判的前提**：方案书、M6、§14.2 多处以"保护 prompt 缓存"为由做了设计取舍（时间与记忆不进系统提示、换人设必须重建会话）。但 JNI 的 `processRawPrompt()` 第一行就是 `reset_long_term_states()`——**每一轮都清空 KV 缓存并整段重算**。也就是说，prompt 缓存在 APK 里从未生效；每轮 20–50 秒的延迟主要就来自这里（见 §4 阶段 B）。

### 1.3 全局记忆与记忆关联

| 问题 | 根因 | 证据 |
|---|---|---|
| 每句话都硬塞记忆 | 每轮把**全部**事实（最多 12 条）注入，没有相关性筛选 | 第 43–55 条每句都提"生日3月15日、周五交周报、冰美式"；第 53 条"3月15日的天气" |
| 记忆干扰动作参数 | 同上，模型把"明天6点"解析成了 2024-03-15 | APK 工程方案 §18.5 |
| 误提取 | 否定模式以"我不"开头即命中：`我不想上班`→「不喜欢想上班」；`我是学生`→「名字：学生」（注释说已排除，代码未实现）；`以后再说`→一条事实；`删掉第2条待办`被当成"忘掉记忆" | `FactExtractor.kt` |
| 无冲突检测、有重复 | 键就是原文，"喜欢香菜"与"不喜欢香菜"并存；"我周五要交周报"与"周五要交周报"并存 | 真实库 facts 表 |
| 设置页"全部清空"会删掉聊天记录 | 事实对话框的按钮调用的是 `clearAll()` | `SettingsActivity.kt` |

### 1.4 为什么同类问题会反复修改（过程层面的根因）

1. **验收样本固定且极少**：每次修复都用同样 4 句冒烟语料验证（"明天6点的日程 / 下午三点开会 / 早上七点闹钟 / 天气"），"4/4 通过"后即标记完成。换一种说法、换一个人设、在闲聊轮出现，就是"新"问题。
2. **修症状不修结构**：每次在 `AgentLoop` 里加一个关键词、加一层判断，而"模型文本就是事实"这一结构从未改变。
3. **完成标准由实现者自评**：里程碑文档的"✅ 完成"依据是截图和少量日志，没有可重复执行的回归测试；所有测试都必须真机 + adb + 截图，成本高，自然测得少。
4. **测试数据与真实数据混用**：危机语句、重复冒烟语料都写进了日常使用的同一个数据库，进一步污染了上下文。

## 二、成熟系统应该是怎样的

### 2.1 分层与数据流

```
用户输入
  │
  ├─①安全层（规则，先于一切）──命中危机词：固定话术 + 求助资源，不调用模型
  │
  ├─②理解层（NLU）
  │     确定性意图路由：闹钟 / 提醒 / 待办 / 日程 / 查时间 / 记忆指令
  │     槽位抽取：中文时间解析（程序完成，不交给模型）
  │     对话状态：缺槽位就追问，下一句补齐后执行（多轮补槽）
  │
  ├─③执行层（动作账本）
  │     每个副作用 → ToolOutcome{VERIFIED / UNVERIFIED / FAILED / INFO, 回执, 类别}
  │     执行后核验：回读文件、查询日历、核对系统下一个闹钟、AlarmManager 接受
  │     账本落库（actions 表），可审计
  │
  ├─④生成层（模型，只负责"怎么说"）
  │     开放式对话、程序无法理解的请求 → 模型（可带工具）
  │     动作已由程序完成时 → 模型只写一句人设口吻的话（或直接用人设短句，不调用模型）
  │
  └─⑤守卫层（程序，最后一道）
        逐句扫描模型输出：任何"已设好 / 记住了 / 会提醒你"若在本轮账本里没有成功记录 → 整句删除并如实说明
        最终回复 = 人设话语 + 程序回执（回执单独显示，视觉上与"它说的话"区分）
```

**不变量**（任何改动都不得破坏）：
1. 用户看到的"做了什么"只来自账本，不来自模型文本。
2. 账本只记录**核验过**的结果；无法核验的必须明说"未能确认"。
3. 程序承诺的能力必须有对应的执行机制（说"会提醒"就必须登记了定时）。
4. 模型上下文只包含真实对话；模板、回执、系统提示不得冒充 assistant 发言（回执以"系统回执"附注形式出现）。

### 2.2 会话、人格、记忆的作用域

| 数据 | 作用域 | 进入 prompt 的方式 |
|---|---|---|
| 会话消息 | **会话**内；一个会话绑定一个人设 | 只取当前会话、当前人设、近 6 小时、kind=chat 的最近 6 条 |
| 人格 | 人设定义（系统提示 + 后处理 + 话术）是数据；人格状态（情绪阶梯，待做）**按人设**独立 | 系统提示每轮随消息传入，换人设即时生效，无需重载模型 |
| 用户事实 | **全局**（关于用户本人，跨人设共享） | 按与本轮输入的相关性挑选 ≤3 条，名字/称呼常驻 |
| 会话摘要（待做） | 会话级，跨会话检索 | 相关时注入一两句"上次聊到……" |
| 动作账本 | 审计，不属于记忆 | 不进 prompt，只给用户核对 |

**会话管理**的成熟形态：会话列表（标题取首句、时间、人设头像）、新建、切换（人设随会话切换）、删除、超时自动分段、会话结束后在空闲时生成摘要。**人格切换** = 开新会话（或切回该人设的旧会话），而不是在同一段历史里换个系统提示。

**记忆关联**的成熟形态（由浅到深）：①相关性筛选（本次已做：关键词二字组重叠 + 话题触发词）；②事实槽位化与冲突消解（本次已做：同一对象只保留最新态度）；③事实带来源消息与时间、用户可查看/编辑/删除；④会话摘要与情节记忆；⑤向量检索（手机端可用小型中文嵌入模型，数据量大了再上）。

| 10 | 按返回键退出，再从桌面打开 | 不出现"模型加载失败" |
| 11 | 设置 → 最近动作记录 | 能看到上面每一次动作及其状态 |

> 若第 4 项总是"已改用助手闹钟"，多半是 vivo 的"应用跳转确认"拦截了时钟 Intent：在弹窗里点一次「始终打开」即可（README 已记录这一机制）。

### 阶段 B 的核心改动（`ai_chat.cpp` 的 `processRawPrompt`）

现状每轮都 `reset_long_term_states()` 清空 KV 后整段重算。系统提示 + 工具定义 + 历史在相邻两轮之间绝大部分相同，改为"只重算差异部分"：

```cpp
static llama_tokens g_prev_tokens;   // 上一轮已在 KV 里的 prompt token

// processRawPrompt 内，替换 reset_long_term_states() 与整段 decode：
reset_short_term_states();
auto tokens = common_tokenize(g_context, prompt, true, true);
size_t keep = 0;
while (keep < g_prev_tokens.size() && keep < tokens.size() && g_prev_tokens[keep] == tokens[keep]) keep++;
if (keep == tokens.size()) keep--;                       // 至少重算最后一个 token 以取得 logits
llama_memory_seq_rm(llama_get_memory(g_context), 0, keep, -1);   // 删掉分叉点之后（含上一轮生成的）全部 KV
llama_tokens suffix(tokens.begin() + keep, tokens.end());
if (decode_tokens_in_batches(g_context, g_batch, suffix, keep, true)) return 2;
system_prompt_position = current_position = (int) tokens.size();
stop_generation_position = current_position + n_predict;
g_prev_tokens = tokens;
common_sampler_reset(g_sampler);
// 注意：shift_context() 触发后位置会变，必须清空 g_prev_tokens；unload() 时也要清空
```

配合 Kotlin 侧：系统提示与工具定义保持在 prompt 最前且逐字不变（本次已满足：时间、记忆都在用户消息里）。改完需要重新编译原生库并实机测速。

### 工作方式建议（同样适用于 AI 编程助手）

"说办了却没办"不只发生在手机助手身上，也会发生在帮你写代码的 AI 身上。要求它交付时附上**证据**而不是结论：编译输出、自检报告、数据库查询结果、实机截图；"✅ 完成"只在验收清单逐项通过后才能写。

## 附：已知局限

1. 意图路由覆盖的是高频、可枚举的说法；非常规说法仍会交给模型，模型若不调工具，守卫会删掉虚假承诺并提示用户换个说法——不会撒谎，但可能需要用户再说一次。
2. 守卫基于句式规则，极个别隐晦的承诺（如"才不是特意为你设闹钟呢……就当提醒你别赖床"）可能漏网；这类请求现在由程序直接执行，基本不会再走到模型。
3. 系统时钟的闹钟无法由本应用取消或修改（Android 没有公开接口）；助手闹钟与助手提醒可以在设置页取消。
4. 有更早的系统闹钟时，新设的闹钟无法自动核对，回执会如实标"未能确认"。
